# L1 Git reference

[Back to the README](../README.md).

L1 Git is a desktop Git client in the L1 family, built with Tauri 2, React, and TypeScript. It browses real local repositories and reads their branches, tags, stashes, submodules, commit history, and commit details. Its Rust core fetches remotes and fast-forwards local branches that are strictly behind their upstream. It pushes the current branch to its configured upstream, and it publishes a branch to an existing remote or to one that **Add remote** creates. Fast-forward refuses a checked-out branch whose tracked files have uncommitted changes.

All local writes go through one guarded write path in the core. L1 Git stages, unstages, and discards files, hunks, and lines. It commits, amends, and edits the last commit's message. It creates, renames, deletes, and checks out branches, checks out commits, creates and deletes tags, and stashes, applies, pops, and drops changes. It undoes and redoes each of those writes. It merges any local or remote branch into the checked-out branch after a review, cherry-picks or reverts one commit, and resolves text conflicts in its own resolver. It pulls the checked-out branch with a fast-forward, a merge, or a rebase, and it does not resolve rebase conflicts. **Try it locally…** checks a branch out in a linked worktree of its own, and the same branch menu removes that worktree. A pull request's **Try it locally** does the same for its head, on the branch `pr/<number>`, and keeps it current. L1 Git can also connect to GitHub with the sign-in of the GitHub CLI, read pull requests there, and write to them when you click.

See [Releasing L1 Git](releasing.md) for nightly and stable downloads, signing setup, and recovery.

## Run the desktop app

Install Git 2.45 or later, Node.js 26, pnpm 10.32.1, Rust 1.93 or later, and the native Tauri build dependencies. On macOS, install Xcode and its command-line tools. On Windows 10 or later, install Git for Windows with Git on `PATH`, the MSVC Rust toolchain, Microsoft C++ Build Tools with the Desktop development with C++ workload, and Microsoft Edge WebView2 Runtime. Run the commands below in PowerShell. See the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) for native setup details.

```sh
pnpm install --frozen-lockfile
pnpm tauri dev
```

If macOS selects the standalone command-line tools instead of Xcode, start with:

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer pnpm tauri dev
```

Click **+** at the top of the sidebar or press **Cmd/Ctrl+O**, then choose a source. Type to filter the sources, press Up and Down to move through them, and Enter to open one. Escape or a click outside closes the palette from any step, and focus returns to where it was. The back arrow returns to the sources.

- **New repository** runs `git init` at the location shown under the name. The location follows the name until you edit it, under `~/Projects`, or `~` when that folder does not exist. Missing folders are created. An existing folder keeps its files and starts being tracked. A folder that is already a repository is refused.
- **Git URL** clones to a location named after the URL, which you can edit. A folder that has files is refused. Git never prompts, so a remote that needs credentials must already have them. Escape during a clone stops it and removes what it copied, keeping a folder that existed before.
- **Local folder** lists the folders at the typed path, or those that start with its last segment, and labels each one **Git repository**, **Bare repository, not supported**, or **No Git repository**. A path inside a repository lists that one directory. Dot-folders appear only when the typed segment starts with a dot, and the list stops at 500 folders. Up and Down move the highlight from anywhere in the step. Enter or **Open** adds a highlighted repository. A double-click adds a repository or enters another folder, and Right Arrow with the caret at the end of the path enters the highlighted folder. Backspace returns to the sources from an empty path or from a button. On macOS, the list of your home folder does not look inside Desktop, Documents, Downloads, Movies, Music, or Pictures, which would raise a permission prompt, so they show as **No Git repository** until you open them.

You can open a subfolder or symlink. L1 Git saves the canonical working-copy root and keeps linked worktrees as separate repositories. A new repository joins the end of the sidebar list. Opening a repository again keeps its place. When two repositories share a folder name, the sidebar shows, dimmed after each name, the fewest parent folders that tell them apart. The command palette adds the same folders in parentheses, such as `l1-demo (l1git-fixture-8jd73m)`. L1 Git cannot open a bare repository. A typed path at or inside one lists that directory as **Bare repository, not supported**. While that row is highlighted, **Open** is unavailable and the palette says `Bare repositories are not supported yet. Choose a working copy of this repository.`

L1 Git opens on your last repository and fetches every saved repository. Linked worktrees of one repository share one fetch. The **Fetch** menu in the repository toolbar, and the command palette, offer **Fetch** and **Fetch all**. **Fetch** fetches one branch without pruning. It takes the sidebar branch you last selected, or else the checked-out branch. A remote branch fetches itself, and a local branch fetches its upstream. When **Fetch** cannot run, such as for a local branch with no upstream on a remote, it is unavailable in the menu and absent from the command palette. **Fetch all** fetches every remote of the open repository. After a fetch that reached a remote, a notice above the history names the remotes and how many branches moved, such as `Fetched origin. 2 branches moved.` A fetch that fails, in part or in full, posts no notice and keeps the notice already shown, and the failure shows as a warning. In the sidebar, each repository and local branch shows how many commits it has to pull and push.

When some branches of the open repository are behind their upstream and clean, the command palette offers **Fast-forward all branches (N)**. It moves exactly those branches. A branch checked out in a worktree with uncommitted changes, or in a worktree in the middle of a merge or rebase, is not counted. A diverged branch is never counted. To move one branch, right-click it in the sidebar and choose **Fast-forward to origin/main**, which names the branch's upstream. The item moves only that branch, and its tooltip says that a fast-forward has no Undo entry. When the item cannot run, it stays in the menu, unavailable, with its reason. That happens when the branch is up to date, only ahead, or diverged. It also happens when the branch is checked out in the open worktree, or in a worktree that has uncommitted changes or an operation in progress. For a branch that is behind and checked out in the open worktree, the reason says to use Pull. A remote branch, a branch with no upstream, and a branch whose upstream is gone show no item. After either fast-forward, a notice names the branches that moved, such as `Fast-forwarded main.` A fast-forward that moves nothing posts no notice.

The **Push** menu in the toolbar, and the command palette, offer **Push to origin/main**, named after the current worktree's configured upstream remote and branch. **Push to origin/main** is unavailable when the branch has no commits that its upstream lacks. Its tooltip and palette detail say why, such as `Nothing to push. main is 2 behind origin/main. Pull first.` or `Nothing to push. main is up to date with origin/main.` L1 Git counts only against the remote-tracking branch of that destination. Push stays available when the remote has a separate push URL or the count is not available. A diverged branch keeps Push available. If the remote rejects the push, the notice names both counts, such as `Push rejected. feat/x has diverged from origin/feat/x (1 ahead, 1 behind). Pull, then push again.` Push publishes the current branch tip recorded when the destination was prepared. It refuses a changed checkout, commit, or destination until you review the refreshed target. Uncommitted files stay local. Push uses your Git credentials, signing settings, and hooks, with interactive prompts disabled. For a branch without tracking settings, the same item reads **Publish branch…** in both the toolbar and the command palette, and it opens a dialog. Choose an existing remote and a destination branch, then click **Review publication**. The review shows the full source commit, destination ref, and effective push endpoint with credentials removed. Changing either field requires a new review. Click **Publish branch** to send the reviewed commit.

Push updates one branch with ordinary non-force semantics. It does not publish tags or other branches, recurse into submodules or create an Undo entry. Ordinary Push keeps the existing upstream. Publish branch sets the upstream only after Git confirms publication. Mirror remotes, multiple effective push URLs, and local upstreams are unsupported. A single separate push URL and custom fetch mappings are supported. After a push, L1 Git refreshes local counts without fetching. The result shows in the notice above the history, such as `Pushed main to origin/main.` **Dismiss** closes it. The next push, pull, or write replaces it, except staging, unstaging, **Save result**, and the other writes that post no notice. When one of those works, it leaves the notice in place, except that it clears the notice of a write that failed. If Git cannot confirm publication, the notice says the result is uncertain. Check the remote before retrying. A confirmed push stays confirmed even if the local refresh fails. Publication also stays confirmed if upstream setup fails. Its notice reports tracking and refresh problems separately. A new destination, an equal destination, or a fast-forward is allowed. Divergent history is refused.

Before either push mode, L1 Git refuses fetch mappings into local branches, tags, or symbolic refs. Transport does not update tracking refs implicitly. After confirmed publication, L1 Git updates only the captured tracking refs without following symbolic refs, and only while their old commits still match. If those refs changed or cannot be updated, the published result remains confirmed and the notice asks you to fetch for current counts.

Publish branch requires both `branch.<name>.remote` and `branch.<name>.merge` to be absent. Partial or ambiguous tracking settings need attention in Git. The chosen destination must have one usable fetch mapping, including custom mappings, and must not be excluded by a negative refspec.

To connect an existing endpoint, click **Add remote…** inside Publish branch. Enter a Git remote name and a URL, SSH endpoint, or filesystem path, then click **Add remote**. The name starts empty when the repository already has a remote named `origin`. Otherwise it starts as `origin`, selected, so typing replaces it. When Git refuses the remote, such as for a duplicate name, the dialog keeps the URL and selects the name. A URL that holds a user name or password is cleared instead, and the URL field gets focus. The app saves the URL and standard fetch mapping together, selects the new remote, and keeps your destination. Adding a remote does not fetch, publish, set an upstream, or create an Undo entry. Click **Review publication** and then **Publish branch** to publish. Duplicate names from effective Git config are refused, including included, global, and worktree settings. A saved remote stays saved if refreshing its choices fails. Click **Reload remotes** to retry the read. If the connection to the app's Git bridge is lost, reload remotes to check whether the addition completed before retrying. Remote creation on a hosting provider, remote editing, and removal remain outside this dialog.

After transport, L1 Git checks the original checkout, commit, and relevant settings again before setting tracking. It stages both tracking keys and installs them together under the common config's standard lock, preserving unrelated settings and permissions. Ordinary includes and worktree config are supported. Changes to independently edited global, included, or worktree config cannot all be locked together. Immediate checks and readback detect relevant changes but cannot freeze those external files.

The graph shows one repository at a time, with all of its local and remote branches. The sidebar lists your repositories, and below them the refs of the open repository only. Click a repository to open it in the graph. The history shows a placeholder until the first read finishes, and its heading names the repository, such as `l1-demo commits`. L1 Git keeps the snapshots of the eight most recently opened repositories in memory. Returning to one of them shows its graph at once, with the commit you selected and the scroll position you left, then rereads it in the background and updates the graph if anything changed. If the selected commit is gone, the newest commit is selected. A branch you click in the sidebar takes precedence over the remembered commit. Click a branch in the sidebar to select its tip and scroll the graph to it. Nothing is checked out. The sidebar lists branches under **Local** and **Remote** and groups them into folders at each slash in their names, so `feat/ui/x` sits in `feat`, then `ui`. Remote branches group by remote first. Folders start closed, except the ones that hold the checked-out branch or the branch you last selected. A search opens every folder that has a match. The checked-out branch has a `HEAD` badge and a tinted background. When its folder is closed, the folder gets the tinted background instead. L1 Git rereads local state, including the open repository's branches, whenever its window regains focus, so commits and branches you make in a terminal appear when you switch back. The open history and its branches also refresh after a fetch or fast-forward moves their refs. Remote branches reflect refs already on disk, usually from your last fetch. A fetch removes remote branches that were deleted on the remote, such as a merged pull request branch. Local branches stay, and a local branch that tracked one shows that its upstream is gone.

Below **Remote**, the sidebar lists **Tags** and **Stashes**, each with its count, and **Submodules** when the repository has any. Tags sort by name with numbers in numeric order, so `v1.10.0` follows `v1.9.0`. Click a tag to select its commit and scroll the graph to it, as with a branch. When soloed branches leave a tag's commit out of the graph, a notice says so and offers **Show all branches**. Stashes list newest first, each with its message and its `stash@{n}` name. The row leaves out the branch that Git puts first in the message, and its tooltip keeps it. Click a stash to show its changes in the inspector, compared with the commit it was made on, as `git stash show` does. The inspector names that commit as the stash's only parent. Select a changed file to open its diff. The history never lists a stash, so the graph draws no stash row. A stash saved with `--include-untracked` shows only its tracked changes. Right-click a stash, or focus it and press Shift+F10 or the context menu key, for **Apply**, **Pop**, and **Drop…**. **Drop…** asks first. Submodules list each path that `.gitmodules` maps, with the commit the index records for it, or the commit HEAD records while the path has a merge conflict. When a sparse checkout leaves `.gitmodules` out of the working tree, L1 Git reads it from the index. A gitlink at a path that `.gitmodules` does not name is left out, and so is a submodule whose path is not valid UTF-8. When Git cannot read the stashes or the submodules, that section is left out and the rest of the sidebar still loads. The sidebar search filters tags by name, stashes by message or name, and submodules by path. Each section opens and closes on its own. The command palette lists the open repository's tags and stashes too, and finds a stash by its message or its `stash@{n}` name.

A commit's menu in the history offers **Create tag…**, which opens a dialog with **Tag name** focused and an optional **Message**. Press Enter in the name field, or Cmd/Ctrl+Enter in the message, to create the tag. With no message the tag is lightweight. With a message it is annotated, and Git records you as the tagger and signs it when `tag.gpgSign` or `tag.forceSignAnnotated` asks. When Git refuses the name, its reason shows under the field and the dialog stays open, such as `'v0..1' is not a valid tag name.` or `A tag named 'v0.1.0' already exists.` A signing or identity error also shows in the dialog. Right-click a tag under **Tags**, or focus it and press Shift+F10 or the context menu key, for **Delete tag…**, which asks first and says whether the tag is annotated or lightweight and which commit it points at. Both writes act on the open repository's tags only. The palette offers **Create tag…** for the selected commit and **Delete tag v0.1.0…** for the sidebar tag you last selected. **Undo** and **Redo** undo and redo each of them, as **Undo Create tag v0.2.0**. Pushing tags is not part of L1 Git yet.

The history contains the newest 50,000 commits reachable from local and remote branches, tags, and HEAD. If a branch tip is older than that, selecting the branch says so. Internal refs and stashes are excluded. Each row shows its branch, tag, or worktree labels to the left of the graph, then the commit message. The first label sits next to the commit's graph line and `+N` lists the rest. A worktree icon marks a branch checked out in another worktree. Each graph node shows the author's initials. Hover a node for the author's name and email. Graph connections use actual parent IDs. Dashed edges lead to parents beyond the loaded history.

Right-click a branch in the sidebar, or focus it and press Shift+F10 or the context menu key, for **Hide** and **Solo**, then **Check out**, **Fast-forward to origin/main**, **Merge into current branch…**, **New branch…**, **Rename…**, and **Delete…**, then **Try it locally…** and **Remove worktree…**. Each item appears only for a branch it applies to. An item that cannot run stays in the menu, unavailable, with its reason under its name, such as `Checked out in sync-develop`. A commit's menu in the history also offers **New branch…**. These writes act on the open repository's branches. **New branch…** and **Rename…** open a dialog with the name field focused. Press Enter to create or rename. When Git refuses the name, its reason shows under the field and the dialog stays open, such as `'bad..name' is not a valid branch name.` or `A branch named 'main' already exists.` A new branch gets the upstream `git branch` would give it under `branch.autoSetupMerge`, so by default a branch made from a remote branch tracks it. The new or renamed branch is then selected, as if you had clicked it. **Delete…** is unavailable for a branch that a worktree has checked out and says which worktree. Otherwise it asks first and says whether the branch is merged into HEAD and into its upstream, naming each one it is not merged into. The command palette offers the same three writes for the sidebar branch you last selected, as **New branch from main…**, **Rename main…**, and **Delete main…**. Like most palette actions, each is listed only when it can run, so the palette leaves out **Delete…** for a checked-out branch, which the sidebar menu shows as unavailable, with the worktree that has it. **Undo** and **Redo** in the toolbar's **More** menu, and Cmd/Ctrl+Z and Cmd/Ctrl+Shift+Z, undo and redo each of them, as **Undo Create branch topic**.

Double-click a local or remote branch in the sidebar to check it out, or choose **Check out** in its menu. HEAD's label in the history and the tinted background in the sidebar move to it. **Check out** is unavailable for the branch HEAD is on and for a branch another worktree has checked out, and says which. A remote branch checks out the local branch of the same name, such as `feat/x` for `origin/feat/x`, and creates that branch tracking the remote one when it does not exist. A commit's menu in the history offers **Check out this commit…**, which first asks, because HEAD will be detached at that commit and new commits will belong to no branch until you create one. **New branch…** has a **Check out after create** box, which creates the branch and then checks it out, as two steps you undo one at a time. Uncommitted changes come along when Git can carry them. When it cannot, the notice names the files and nothing changes. L1 Git never stashes them for you. The palette offers **Check out main** for the sidebar branch you last selected. Undo checks out where HEAD was, as **Undo Check out feat/x**, and deletes a branch that checking out a remote branch created. When a `post-checkout` hook fails, the checkout stays, and the notice shows the end of the hook's output.

Choose **Try it locally…** in a branch's menu to check the branch out in a linked worktree of its own. Your current branch and uncommitted changes stay as they are. The dialog proposes a folder beside the main worktree, such as `~/src/.worktrees/l1git-feat-x` for `feat/x` in `~/src/l1git`, and you can edit it. Missing folders are created, and a folder that has files is refused. The dialog also names the local branch. A local branch checks out as itself. A remote branch checks out the branch **Check out** would use, created tracking the remote branch when it does not exist. **Try it locally…** is unavailable for a local branch that a worktree has checked out, as **Check out** is, and the dialog refuses a remote branch whose local branch a worktree has. Click **Create worktree**. When Git refuses, its reason shows under the fields and the dialog stays open. The new worktree joins the end of the sidebar as its own repository, and a notice offers **Open worktree** and **Stay here** while the repository you made it from is open. L1 Git never opens the worktree on its own. When a `post-checkout` hook fails, the worktree stays, and the notice shows the end of the hook's output. A branch that a linked worktree has checked out gets **Remove worktree…** in its menu, unavailable while that worktree is the open repository. It asks first. Git then deletes the folder, including ignored files such as dependencies and build output, and the sidebar drops it. A notice says `Removed worktree l1git-feat-x. Removal cannot be undone.` and replaces the notice shown before. The branch and its commits stay. L1 Git refuses to remove the main worktree, a locked worktree, a worktree with uncommitted or untracked files, and a worktree in the middle of a merge, rebase, cherry-pick, revert, or bisect. It never forces. Neither write has an Undo entry. Removing a worktree drops the Undo entries made in it, so Undo goes on to older entries. The palette offers **Try feat/x locally…** and **Remove worktree l1git-feat-x…** for the sidebar branch you last selected.

Right-click the history's column headers to choose which columns follow the commit message. Right-click a commit, or press Shift+F10 or the context menu key while the history has focus, for a menu that offers **Compare with working copy** and **Pick for comparison** above the same columns. **Author** shows the author's name. **Age** shows when the commit was authored, as a short relative time such as `3d` or `2mo`. Hover an age for the full date and time. **Commit ID** shows the shortest commit ID prefix, at least seven characters, that no other loaded commit shares, and widens to fit the longest one. Hover it for the full ID. **Changes** shows how many lines each commit added and deleted, such as `+4 −2`, and shortens a count of 10,000 or more, such as `12K`. **Age** and **Changes** are on at first. A column choice you saved before stays as it was. Hiding **Changes** stops L1 Git from counting lines. Turning on any column other than **Changes** narrows the commit message's minimum width so more columns fit. When the menu closes, the history scrolls sideways to show the last column you turned on if it is out of view. Press Up and Down to move through the menu, Home and End to jump to the first and last item, Space or Enter to toggle a column, and Escape to close it. The app saves your columns on this device, and every repository uses the same ones.

Select a commit to inspect its message, author, date, parents, and changed paths. Changed paths appear as a file tree with added, modified, and deleted markers. Directories start open, and single-child directory chains collapse into one row. Select a file to replace the history with its diff against the same base. Use **Unified** or **Split** to change the layout. Click **Back to history** or press Escape to return. Selecting another commit closes the diff. Between two hunks, a row counts the unchanged lines the diff hides, such as `12 unmodified lines`, and expanding it shows them. L1 Git reads the rest of the file only when you expand, so before the first expand a row after the last hunk says that more unchanged context may be available. A file whose full diff is larger than 1 MiB does not expand. **Toggle commit inspector**, at the top right of the window and in the command palette, hides and shows the inspector. Binary files and patches larger than 1 MiB show a notice instead of a diff. Merge changes are compared with the first parent. Root commits use the empty tree. Renames appear as a deletion and an addition. Parent links can open details outside the loaded history. Partial clones report a read error when required objects are missing locally. L1 Git never fetches them for a read. Only a discard fetches the blobs it puts back.

Click **History** next to **Unified** and **Split** to list the commits that changed the open file, newest first. **Show file history** in the toolbar's **More** menu and in the command palette does the same. The list starts at the selected commit, or at the target of a comparison, and follows the file back through renames, as `git log --follow <commit> -- <path>` does. A row whose path differs from the open file's names the path the file had in that commit. Select a row, or Tab to the list and press Up, Down, Home, or End, to show that commit's diff for the file below the list. The diff uses the Unified or Split layout you last chose. Click **Blame**, or choose **Show blame**, to show the file as it is in the selected commit, with a band above each run of lines naming the author, the age, the short commit ID, and the subject of the commit that last changed them. Click a band, or a line number, to select that commit in the graph. The bands are buttons, so Tab reaches them and Enter selects. A band for a commit that a hidden branch leaves out of the graph, or that is older than the loaded history, cannot be selected. Blame can name a merge commit for lines the merge itself changed, and History does not list that merge, because `git log --follow` leaves merges out. Blame names authors as the graph does, without `.mailmap`, and ignores any `blame.ignoreRevsFile` setting. Blame shows a notice instead of the file for a binary file, a file larger than 1 MiB, a submodule, a file the commit deleted, and an empty file. History and Blame need a commit, so they are unavailable for a worktree's staged and unstaged files and for a comparison with a working copy. Escape closes the file and returns to the history with the commit still selected.

Press Cmd and click a second row on macOS, or Ctrl and click on other systems, to compare it with the selected row. The older commit is the base and the newer one the target. A worktree row is always the target, so a commit compared with it shows what changed between that commit and the files on disk, untracked files included. The list reads again whenever L1 Git rereads that worktree's status and finds a change. A file removed from the index with `git rm --cached` but still on disk reads as deleted, as `git diff <commit>` shows it. Two worktree rows cannot be compared. Choose **Compare with working copy** in a commit's menu to compare it with the open repository's own working copy, even when it has no uncommitted changes. To compare two commits from the keyboard, choose **Pick for comparison** in the first commit's menu, move to the second, and choose **Compare with** followed by the first commit's short ID. A gray pin before its message marks the picked commit. Picking another commit replaces the pick, **Clear pick** in the picked commit's menu drops it, and starting any comparison clears it. The selected row keeps its selection color and the compared row takes the plain selection color and a dashed ring around its node. The inspector heading shows both ends as short IDs and a **Swap** button that reverses the base and the target of two commits. The inspector lists each end's subject with a link that selects that commit alone, then the paths that differ. A commit compared with itself says there are no changes. Select a path to open its diff between the two ends. Click a row without the modifier, or press Escape while the history has focus, to stop comparing and keep the selected row. When a diff is open, the first Escape closes it and the second stops comparing. A compared commit that a hidden branch leaves out of the graph stays compared, as a hidden selection stays selected.

Each worktree of the open repository that has uncommitted changes gets a row directly above the commit it has checked out. The row carries the worktree's name, a dashed node, and **Uncommitted changes** with a count of each kind, such as `1 modified, 1 untracked`. When the row is narrow, the **Uncommitted changes** label shortens before the counts do. A worktree with no changes gets no row. No commit moves to another lane because of a row. When no newer commit in the graph connects to the commit, the row shares the commit's lane. Otherwise the row takes a new lane to the right of the lanes that pass it. A branch pointing at the commit does not change this. Hiding a branch never hides a row, because a worktree's commit always stays in the graph. Soloing branches whose history leaves out a worktree's commit hides that row. A worktree whose commit is older than the loaded history has no row. A worktree that has no commits yet gets its row at the top, under any rule. Select the row, or reach it with the arrow keys, to list its changed paths in the inspector under **Conflicts**, **Unstaged**, and **Staged**. Shift+Down from the row selects its commit. When the row shares the commit's lane, Shift+Up from the commit returns to the row. A file with staged and unstaged edits appears in both lists. A staged rename appears under its new path, and a later edit to it appears under **Unstaged** as a change to that path. An untracked nested repository appears as one entry. Select a path to open its diff with a **Staged**, **Unstaged**, or **Conflict** tag. A staged diff compares HEAD with the index, as `git diff --cached` does, and an unstaged diff compares the index with the working tree, as `git diff` does. An untracked file shows as wholly added. A conflicted path opens the text resolver when its representation is supported. Other conflicts explain why they need external resolution. A submodule says what changed inside it. A pure rename says which path it came from. When Git cannot read a path, its error appears in place of the diff, and a path that changed during the read offers **Refresh**. L1 Git reads each worktree's status when the repository opens, when the window regains focus, and after a fetch moves the repository's refs. It never polls. When a reread changes the open path, its diff reloads in place. When the path left its list for another, as a stage or an unstage moves it, the diff follows it there and takes that list's tag. When no list has the path, the diff closes. When a selected worktree's changes are gone, the newest commit is selected. Search never matches a worktree row, and the Author, Age, Commit ID, and Changes cells of a worktree row are empty.

Ordinary both-modified text conflicts from stash apply or pop, a merge, a cherry-pick, or a revert open in the conflict resolver. **Base**, **Current**, and **Incoming** under **Git index versions** show the three Git index versions. **Choices** provides Pierre's current, incoming, and both controls. **Edit** opens the result in Pierre's text editor. The initial result is the working file, including any conflict markers. **More actions** offers **Take all Current** and **Take all Incoming**, which replace the whole result with that side, then **Copy result**, **Reload from disk…**, and **Refresh conflict**. After a **Take all** choice, a notice such as `Took all of Current.` offers **Undo** until you edit or save the result. **Save result** writes only that file. **Mark resolved** is a separate action that stages the saved file. It stays unavailable while the result has a conflict or a leftover conflict marker, has unsaved edits, or changed on disk. It is also unavailable while L1 Git saves or reads the file. Its tooltip says why. The first repository Undo restores the conflict stages. The second restores the original working bytes and permissions. Redo repeats Save, then Mark resolved. Undo inside the text editor changes only the draft.

Resolution drafts remain in memory while navigating, refreshing, or switching repositories. **Unsaved conflict results** reopens a dirty draft even if another program resolved the conflict. An external change makes the draft stale and blocks Save. **Copy result** preserves text on the clipboard. **Reload from disk…** requires explicit discard confirmation and preserves edits made after that confirmation. App update consent counts these drafts across worktrees and freezes editors during installation. The browser also requests confirmation before leaving with unsaved results. Drafts are not persisted across an uncontrolled process exit.

The resolver supports regular files with three regular index versions, UTF-8 content without NUL bytes, uniform LF or CRLF endings, and at most 256 KiB per version or result. CRLF, missing final newlines, and permissions are preserved. A binary file, a symbolic link, a file that one side deleted and the other edited, and a file that only one side added open a choice between the two sides instead of the editor. Two cards show what each side keeps. Each card has a button, such as **Keep file** or **Delete file**, and a key, 1 or 2. Choosing a card writes that side to the working file and the index. Undo restores the conflict. Submodules, special files, mode conflicts and other structural conflicts, custom filters, ident expansion, and working-tree encodings require external resolution, and so do symbolic links on Windows. For such a file, the resolver says why and offers **Refresh conflict** and **Mark resolved**, which stages the file as it is on disk without checking it for markers. Git text and eol settings are supported. Mark resolved still uses ordinary Git staging conversions. Saving checks HEAD, target index stages and flags, bytes, file identity, permissions, safe parent directories, and relevant conversion settings. An unchanged result creates no history entry.

## Connect GitHub

Open **Settings**, then **Hosts**, or run **Open Hosts settings** from the command palette. L1 Git connects to GitHub by copying the sign-in of the [GitHub CLI](https://cli.github.com), `gh`, so you never copy a token by hand.

Click **Sign in to GitHub**. L1 Git looks for `gh` on your `PATH` and in the folders its installers use, then runs `gh auth status --hostname github.com --json hosts`, which prints no token. If `gh` is missing, too old, not signed in to github.com, or holds a sign-in GitHub refuses, the dialog says what to run in a terminal. Click **Check again** when you have. When `gh` is signed in, the dialog names the account and the `gh` it found. Click **Sign in as @login** to agree. L1 Git then runs `gh auth token --hostname github.com --user <login>`, asks GitHub's API who the token belongs to, and keeps the token only when it belongs to the account you agreed to. A token without the `repo` scope reads public repositories only. To read private ones, run `gh auth refresh -h github.com -s repo`, then sign in again, disconnecting first if L1 Git is already connected.

The dialog can also sign in through a browser, but only in a build made with `L1GIT_GITHUB_CLIENT_ID` set to the client ID of a GitHub OAuth app that allows device flow. `crates/host` reads the variable at build time, so the app and the bridge agree. Without it, the dialog shows no browser option. With it, **Sign in with a browser** shows a code, and **Open GitHub** opens the page where you enter it. L1 Git connects once GitHub confirms the code. The browser sign-in asks for the `repo` scope, and L1 Git checks and keeps its token like one copied from `gh`.

L1 Git keeps its copy of the token in the system keychain under the service `dev.l1.git`: the login keychain on macOS, Credential Manager on Windows, and the Secret Service on Linux. `host.json` in the app's configuration folder records the login, the API address, and what the token can read, never the token. The token stays in the Rust side of L1 Git, and the window never receives it. L1 Git reads the account the token belongs to, a repository's open and recently merged pull requests, and one pull request in full. It writes to GitHub only when you click a button that says what it sends, and never in the background. It reads pull requests for the [pull request list](#pull-requests), and nothing before you first open it. Launching L1 Git reads `host.json` and never the keychain, and opening Settings reads neither, so neither brings up a keychain prompt.

**Check connection** asks GitHub who the saved token belongs to, and updates the login and what it can read. When GitHub accepts the token, the row says so under the login. A new sign-in shows the same line. If GitHub no longer accepts the token, or the keychain no longer holds it, L1 Git forgets the connection and says why above **Sign in to GitHub**. **Disconnect** asks first, then removes the record from `host.json` and the token from the keychain. It does not revoke the token on GitHub, so `gh` stays signed in. Signing out of `gh` later does not disconnect L1 Git either.

### Writing to GitHub

These are the rules every write to GitHub keeps.

A write is one click, made for the account signed in when you click. If L1 Git is signed in as someone else by the time it sends, it sends nothing. L1 Git sends each write once and never sends it again on its own, even when no answer comes back.

Before a write leaves, L1 Git saves a record of it in `drafts.json`, with the drafts it carries, and reads what is already on GitHub where its result would appear, which is your reviews on the pull request, the thread's comments, or the conversation's comments. A pull request takes one write at a time. While a write is on its way, or while L1 Git can't tell how one ended, the pull request takes no other write, from this window, another window, or another copy of L1 Git on the same configuration folder. While it is on its way, each of them shows it as sending, and none of them can keep it as a draft or send it again. While a window shows a write as sending, it reads `drafts.json` again every 5 seconds, and whenever it gets the focus, so it learns when the write ends and how. A copy of L1 Git that quits or crashes while sending lets go of the write, which then may have posted. The record and its drafts stay through a restart, a crash and signing in again, and a draft a write carries can't be sent again or typed over until the write is known. Words a window typed there before it learned of the write wait in `drafts.json`, so closing the window loses none of them. When the write ends, they replace what it gives back if they were typed on the very draft it carried, and become a new draft if GitHub has it. Typed on an older draft, they stay beside what the write gives back, for you to keep yours or take theirs.

Each write ends in one of four ways:

- **Done.** GitHub did it. The drafts it sent are deleted, and what you wrote shows as sent until L1 Git reads the pull request again.
- **Refused.** GitHub answered and did not do it. L1 Git shows GitHub's reason, and the drafts it carried are drafts again.
- **Not sent.** Nothing reached GitHub, for example because L1 Git could not reach it, the sign-in changed, or the request never got past L1 Git itself. The drafts it carried are drafts again, and you can send it again.
- **Unknown.** L1 Git sent it and got no answer it could read, so it may have posted.

**May have posted** is what L1 Git says of an unknown write until it knows. Each time L1 Git reads the pull request, it looks again. A write that would post twice if sent again (a comment, a reply, Add single comment, Finish review, or submitting a pending review) counts as posted only when GitHub shows something new since L1 Git's read before sending, made by you, with the same words, and for a review the same verdict and line comments. Seeing nothing never counts as not posted, because GitHub may still be working on it. A resolve, an unresolve, a merge or deleting the head branch can be done twice without harm, so L1 Git settles it from what it reads, such as whether the thread is resolved, the pull request merged, or the branch gone. If GitHub hasn't done it, L1 Git says so, and you can send it again. A read GitHub answers only in part counts as no read: L1 Git sends nothing after it and settles nothing from it.

Until L1 Git knows, a write that may have posted offers three choices:

- **Open on GitHub** shows the pull request on github.com, so you can check yourself.
- **Keep as draft** gives its words back to the box as drafts, marked as may have posted, and the pull request takes writes again. Sending them is then up to you.
- **Send anyway** sends the same write again, and warns that it may post twice. L1 Git reads GitHub first, and if the write is there by then, it sends nothing. If GitHub refuses the second send, or L1 Git can't send it, that says nothing of the first, so the write still shows as may have posted, with these choices.

A merge names the head you saw, so a push while you confirm makes GitHub refuse it. Before L1 Git deletes a merged pull request's head branch on GitHub, it checks that the branch is still at the merged commit, that it is not in a fork, and that no open pull request has it as its head or its base. GitHub then deletes the branch only if it still points at that commit, so a push after the check keeps it. A branch that is already gone counts as deleted. Request changes needs a summary, as GitHub requires.

## Pull requests

Click **Pull requests** beside **Settings** at the bottom of the sidebar, or run **Show pull requests** from the command palette. The list covers every saved repository that is on GitHub. A repository counts as the one its `upstream` remote names when that is on github.com, else its `origin`, else its first remote that is. Several clones or worktrees of one GitHub repository are one entry, named like the first of them in the sidebar. Saved repositories that are not on GitHub are left out, and a line under the list says how many there are.

The sidebar holds the views, the repositories, and the labels of the rows in the view. Uncheck a repository to leave out its rows. Choose several labels to see rows with any of them. The counts follow the checked repositories. **Author**, **Review**, **Checks**, and the search narrow the list further. The search matches titles, numbers, head branches, and authors. **Sort** also groups the rows by repository. These choices last until you close the app.

Click a row, or press **Enter** on it, to [read that pull request](#one-pull-request). **Cmd**-click or **Ctrl**-click a row, or click it with the middle button, to open it on GitHub in your browser. The icon is the first of these that applies: merged, closed, draft, checks failing, checks running, ready to merge, open. Ready to merge means that GitHub finds no conflict, no check failed or is still running, and the review is approved or nothing asks for one. Skipped checks do not count. **Your review** means that GitHub asks you, or a team you are on, for a review. **No access** under **Checks** means that the sign-in cannot read them. The arrow keys, **J**, and **K** step through the rows. **Cmd+F** on macOS or **Ctrl+F** elsewhere moves to the search. **Esc** goes back to the history, which is as you left it. While you type a search, **Esc** clears it first.

L1 Git reads nothing for this list until you open it, so launching the app still never reads the keychain. The first read runs alone, so a locked keychain asks once, and then at most four repositories are read at a time. Each repository's rows appear as they arrive. The open pull requests are read again when you open the list, when you sign in, when you return to the window after a minute, on the **Background fetch** interval while the window is visible, and when you click the refresh button. After your first visit the same happens while you are on the history, so the number on the **Pull requests** button stays true. It counts the pull requests that wait for your review. The recently merged ones are read while their view is open.

GitHub answers with the 50 pull requests that changed last in each repository. When there are more, a line such as `Newest 50 of 133 in jest` says so. **Recently merged** covers seven days. When GitHub cannot answer, the rows you already see stay, and a bar says why. Offline, it says when the list was last read. For a repository that GitHub will not show, it names the repository and the reason, with a link when an organization asks for single sign-on. When the hourly limit is used up, L1 Git waits for it to reset before it reads again by itself.

The list only reads. It does not comment, review, or merge.

### One pull request

A pull request opens in place of the list. The list keeps its place, its filters, and its current row for when you come back. Press **Esc**, click **Pull requests** above the title, or run **Back to pull requests** from the command palette to go back. The sidebar's repository and label filters apply to the list behind it, and choosing a view closes the pull request. The header says where it stands among the rows on the list, and links to GitHub.

**Conversation** holds the description, commits, force pushes, reviews, review threads, comments, and how it ended. Commits of one person in a row are one entry. A review without words is one line. Each thread shows the lines it is about, at least four and at most twelve, and a resolved thread starts closed. **Commits** lists the commits by day, newest first. [**Files changed**](#files-changed) shows the diff. **Checks** groups the checks by result and links each to its page. The arrow keys move between the tabs. A refresh keeps what you are reading where it is, also when entries above it come or go. What you expanded stays so behind another tab, and a visit to the history leaves everything as it was. The pane on the right shows the reviewers, the first checks, the details, and whether the pull request can merge. It has the width of the commit inspector, and **Toggle pull request details** hides it.

The last block of that pane claims only what GitHub reports. L1 Git does not read branch rules, so when GitHub blocks a merge for a reason that L1 Git cannot see, it says only that the merge is blocked. GitHub works out whether a pull request can merge after it is asked, so until it has, L1 Git asks again every three seconds, three times at most. Names are GitHub logins. A team shows as **A team**, because its name needs an access that L1 Git does not ask for.

Text is Markdown, shown in the app's theme. HTML in it is never rendered, and only its words, links, and line breaks stay. Images do not load. Each is a link with its description, or **Image** without one. Links open in your browser. A link without a host leads into the repository on GitHub, and a link to a heading does nothing. A link with an address longer than 2,048 characters is plain words. Text longer than 20,000 characters shows its start until you click **Show all**. L1 Git reads Markdown in the background and gives each text 300 ms. A text that takes longer, or holds too much to show at once, such as a table of thousands of cells, shows as plain text. In a very long conversation, text far above or below the view shows once you scroll near it. Code longer than 10,000 characters shows without colors. A mail link opens with the address only.

A pull request is read when you open it, when you come back to it, when you return to the window after half a minute, every half minute while a check runs and the window is visible, on the **Background fetch** interval, and when you click the refresh button, which reads the lists too. Nothing is read in the background while the keychain is locked or the hourly limit is used up, whichever read met it, and a pull request you open then says so instead of asking when the limit is used up. When its repository is removed from the sidebar, the pull request closes. When a read fails, what you see stays and a bar says why. GitHub answers with the newest 100 commits and timeline entries, the first 100 threads with 50 comments each, and 100 checks, and a line says what is left out. GitHub gives up on some very large pull requests. L1 Git then reads them without their review threads, which can take more than ten seconds, and says so.

Reading changes nothing on GitHub. L1 Git does not request reviewers or run checks. It writes to GitHub only when you click, as [Comment on lines](#comment-on-lines), [Finish review](#finish-review), and [Comment, reply, and resolve](#comment-reply-and-resolve) describe. The only things it changes on your computer are that **Files changed** can fetch commits into your clone, that L1 Git remembers which files you [viewed](#viewed-files), and the copy that [**Try it locally**](#try-a-pull-request-locally) makes when you ask for one.

### Comment, reply, and resolve

The bottom of **Conversation** holds a box that says **Leave a comment. Markdown works here.** **Preview** shows how the Markdown reads. **Comment**, or **Cmd+Enter** on macOS and **Ctrl+Enter** elsewhere, posts it to the pull request's conversation. The box is there on every pull request you can read, your own too, and GitHub decides whether you may comment. When GitHub refuses, its reason shows under the box until you dismiss it, and your words stay. While you type, the words are a [draft](#review-drafts) on this machine, and the line under the box says when it is saved.

Each review thread offers **Reply…**, which opens a box of its own, and **Resolve conversation** or **Unresolve conversation**. Each shows only when GitHub lets you. **Cancel** closes an empty reply box, and **Discard** deletes the words in one. A thread folds once it is resolved.

While a comment or a reply is on its way, its box can't change it. Once GitHub has it, the box empties, and the words show where they went, marked **Sent**, until L1 Git reads the pull request again. GitHub answers with a thread's first 50 comments, so a reply to a longer thread is not in what L1 Git reads. L1 Git then says **Posted. GitHub shows it in the full thread.** and links to the pull request on GitHub. [Writing to GitHub](#writing-to-github) says how a write ends when GitHub refuses it, when it never left, or when it may have posted.

**Timeline** and **Threads** at the top of **Conversation** switch between the conversation as it happened and its review threads. **Threads** lists each thread L1 Git read, by file, one row each. A row says where the thread is, who began it, its first words, how many replied, where it stands, and when it last moved. The filters count their threads:

- **Open** shows every thread that isn't resolved. It is the filter **Threads** starts with.
- **Waiting on you** shows the open threads whose last reply answers a comment you wrote. L1 Git can tell only for a thread it read whole.
- **Outdated** shows the open threads on lines that changed since.
- **Resolved** shows the rest. Under **Open**, a line says how many are hidden, and **Show them** shows them.

Each thread stands one way, so a thread that waits on you counts there and not under **Outdated**. A row opens to its lines and comments, with **Reply…**, **Resolve**, and **Show in diff**, which opens **Files changed** at the thread's file. A thread you reply to or resolve stays in its place until you choose another filter. Opening **Threads** and choosing a filter send nothing to GitHub.

### Try a pull request locally

An open pull request that no worktree has checked out offers **Try it locally** next to **Open on GitHub**. It checks the pull request out on the local branch `pr/<number>` in a linked worktree of its own, in the pull request's repository: the first saved clone in the sidebar that has it, which need not be the repository you have open. Your current branch and uncommitted changes stay as they are. The popover proposes a folder beside the main worktree, such as `~/src/.worktrees/l1git-pr-128` for `~/src/l1git`, and you can edit it. A folder under your home folder shows with `~`, as the core answers the home folder. It names the branch and says where pushes from it go: to the head branch, as in `Tracks origin/feat/replay-ui`, or to a remote that L1 Git adds for the author's fork. When you cannot push to the repository of a pull request from one of its own branches, the branch still tracks that branch, so pulling brings the author's pushes, and it says that GitHub refuses a push from there. Commits stay local when the author does not let maintainers edit the pull request, when the author does and you cannot push to the repository, and when the fork is gone, because Push refuses a branch that follows `refs/pull/<number>/head`. When no remote of the clone is the pull request's repository, it says that L1 Git cannot fetch the pull request, and **Create worktree** is not available. Click **Create worktree**. L1 Git fetches the head first, with your own Git credentials. When Git refuses, its reason shows in the popover, which stays open. The worktree joins the end of the sidebar as its own repository, and L1 Git does not open it. Git runs no hook for it, nor for Update, Replace, or Remove, because a hook may run the pull request's code before you chose to run it. Before you click **Create worktree**, **Esc** or **Cancel** closes the popover and changes nothing. While Create runs, the popover stays open and they do nothing, so a refusal always shows there, with focus on the folder. [What L1 Git changes](#what-l1-git-changes) lists the Git commands.

A bar under the title then says where the copy is and how `pr/<number>` stands against the pull request's head, such as `Checked out locally in ~/src/.worktrees/l1git-pr-128 · at 9c2e1b4, up to date`. It says how many commits the branch is behind or ahead of the pull request, or both, and notes uncommitted changes, an operation in progress, and a worktree folder that is missing. L1 Git reads the copy when you open the pull request, each time it reads the pull request again, after a write that failed, and when you return to the window. When it cannot read the copy, the bar says why and offers **Try again**. A read never fetches, so after the author pushes, the bar says `the pull request has new commits on GitHub` until you update.

- **Update** shows when the branch is behind the pull request, or when your clone lacks its head. It fetches the head and fast-forwards the branch. When the fetched head turns out to lack commits on the branch, Update moves nothing, says so, and **Replace with the pull request…** shows.
- **Replace with the pull request…** shows when the branch has commits that the head lacks, as after the author rewrote the branch or you committed there. It asks first and names how many commits leave the branch, which L1 Git cannot undo. Uncommitted changes stay, and Git moves nothing when the pull request changes the same files.
- **Show in history** leaves the pull request, shows `pr/<number>` when a hide or solo rule hides it, and selects the branch's tip in the history. When the repository you have open is a worktree of the pull request's repository, it stays there. Otherwise it opens the pull request's repository. It waits while **Remove worktree** runs.
- **Remove worktree** removes the worktree, never forced, with the same refusals as **Remove worktree…** in a branch's menu, and the sidebar drops it. The bar and the history's notices say it removed the worktree. When that worktree was the repository you had open, the pull request's repository opens in its place. When the worktree was the pull request's repository itself, because it was the first saved clone with the pull request, another saved worktree of the same repository opens instead. With none saved, nothing opens, as when you remove a repository from the sidebar. The pull request then reads from the next saved clone that has it, and closes when none does. It is not offered when the main worktree has `pr/<number>` checked out. When the head holds every commit on the branch, the branch goes too. Otherwise the branch stays, the bar says `Kept locally as pr/128` and how it stands, and **Try it locally** checks it out again at its own tip.

When a write fails, the bar says why until you dismiss it or a read finds the copy changed. One of these writes runs at a time, and none of them has an Undo entry. While one pull request's copy changes, another one's bar still shows where its copy stands, and its buttons wait and say why when you click them. A merged or closed pull request offers no **Try it locally**, and shows the bar when it has a copy.

### Files changed

**Files changed** shows what a pull request changes, read by Git from your clone of its repository: the first saved one in the sidebar that has it. It compares the pull request's head with the commit where it forked from its base, as GitHub does, so the files and the line counts are GitHub's. If they ever differ from the counts that GitHub reports, a line says so above the diff. Nothing is read or fetched before you open the tab.

Opening the tab asks for the diff. When the clone lacks one of the two commits, as for a pull request from a fork, L1 Git fetches the missing ones at once, by ID, with the [`fetch` command below](#what-l1-git-changes). It uses your own Git credentials, like any other fetch, and not the GitHub sign-in. It adds objects to the clone and creates, moves, and deletes no branch, remote-tracking ref, or tag. A fetch has 300 s, and shares the queue of the other fetches of that repository. You can use the other tabs and go back meanwhile. When a fetch fails, the tab says why and does not try again by itself. Click **Try again**, or **Open on GitHub**.

When drawing the changes fails, the tab says so and offers **Try again** and **Open on GitHub**. The tab keeps showing the commits that it first read. When you open it while L1 Git still reads the pull request again, it waits for that read for up to a second, so that it starts with the newest commits. When someone pushes more or the base branch changes, a bar over the end of the diff says so, and **Show them** or **Show it** reads the new state. A base branch that only moved forward changes nothing, because the pull request still starts at the same commit. Closing the pull request and opening it again reads its newest state.

**One file** shows one file at a time, in the order of the tree on the right. **All files** shows them one after the other in that order, with the current file's header on top, and folds a file when you click the arrow before its name. Switching keeps the file and the line. Click a file in the tree, the current one for its beginning, the arrows above the diff, or the button at the end of a file, or press **J** and **K** for the next and the previous file. **N** and **P** go to the next and the previous change, and on to the next or previous file. In **All files**, they stop at a file that is not read yet, and go on when it is. **V** marks the file [viewed](#viewed-files). The letters work while the tab shows, unless you are typing or a menu, a dialog, or the command palette is open. **Unified** and **Split** set the layout. The layout and the view are kept on this computer for the next time. Between two hunks, a row counts the unchanged lines the diff hides, and expanding it reads the file again with all of its lines. When those come to more than 1 MiB, a bar says so instead. A renamed file is one diff, with its old path above it. A file whose mode changed with its lines says which way. Characters that would turn a path around show as their code points, as in `<U+202E>`. A binary file, a submodule, a mode, an empty file, and a change larger than 1 MiB have words instead of lines.

A review thread is one row at its line, and unfolds to its comments. Threads on an outdated line, on the whole file, or on a line that the diff does not show are together at the top of the file. What you unfold stays unfolded in both views. Threads come from the newest read of the pull request whose head is the one you see, so a comment on newer commits waits until you show those. When GitHub gives up on the threads of a later read, the ones before stay. While you have selected something in the diff, new threads wait until you let go of it. The tree counts the comments of each file. A thread on a file that the pull request no longer changes is in **Conversation** only.

#### Comment on lines

Drag across line numbers in either view, or click one and Shift-click another, or drag the plus that appears in the gutter. A box opens under the range, as **Comment on lines 11–12**. **C** opens it on the change the view is at, the one **N** and **P** went to last. GitHub takes a comment only on the lines of a hunk, all in one hunk, so a range is cut to the hunk it ends in, and one with no line of a hunk opens no box and a bar says why. **Write** and **Preview** switch between the text and how its Markdown reads. The words are a [draft](#review-drafts), so the box says **Saved as a draft on this machine**. **Cancel** deletes a new comment, or puts back the words of one you edit. While the box holds words you typed, choosing other lines, or **C**, opens no other box. The box stays where it is and says **Finish or cancel this comment first.**, so words become a pending comment only through **Start a review** or **Add review comment**. When the box is in another file, the bar over the end of the diff says where it is.

Cmd/Ctrl+Enter presses the box's main button: **Start a review**, **Add review comment**, or **Update comment**. **Start a review** sends nothing. It keeps the comment on this computer as a pending comment, shown under its line with **Pending**, **Edit**, and **Delete**, and it takes the focus. The next box offers **Add review comment**. Pending comments go to GitHub only when you [finish the review](#finish-review). A review goes with the newest commit, so while new commits wait behind **Show them**, **Start a review** waits too, and the box says why. A pending comment written against an earlier commit, or whose lines the diff no longer shows, is never placed on a line. It waits with the file's other comments at the top of the file, with **Delete**.

**Add single comment** posts the comment now, as a review of one comment on the commit you see, also on your own pull request. While it is on its way, the box can't be typed in and says **Sending…**. When GitHub has it, the box closes, and L1 Git reads the pull request again at once, so the comment shows on its line as GitHub has it. Until that read, it shows as **Posted**. When GitHub refuses it or it was not sent, the box says why and keeps your words. When the answer is lost, the box says that it may have posted and offers **Open on GitHub**, **Keep as draft**, and **Send anyway**, as [Writing to GitHub](#writing-to-github) describes. While the box is open in a file, new threads wait until it closes, so the lines you chose stay chosen. While another write carries the words saved at the box's lines, such as a review on its way or a comment another window sent, the box shows them and can't be typed in until that write ends.

#### Finish review

**Finish review** at the end of the toolbar counts the pending comments written against the head GitHub has, as **Finish review · 2**, and opens a popover under it. The popover lists those comments, and choosing one goes to its line. Pending comments written against an earlier commit are listed apart, with **Open at that line**, which opens the file's other comments, and **Delete**. They are never sent, because their line numbers belong to another commit. Reminders say how many files are not [viewed](#viewed-files) yet, with **Show them**, and name up to three unresolved threads, each with **Open**. They never stop a review. An optional summary takes Markdown and is a [draft](#review-drafts) too. **Comment** is chosen first, and **Approve** and **Request changes** follow, except on your own pull request, where GitHub takes a comment only. **Request changes** needs a summary, and a comment with no summary needs a pending comment, and until then the popover says why and sends nothing.

**Submit review**, or Cmd+Enter on macOS and Ctrl+Enter elsewhere, sends the summary, the choice and every listed pending comment as one review, so the author gets one notification. While it is on its way, the popover can't be changed and says **Sending your review…**, and each comment shows **Sending…** on its line. When GitHub has it, the popover closes and **Finish review** takes the focus. The toolbar says **Review sent.** for 8 seconds, or until you open **Finish review** again, and L1 Git reads the pull request again at once, so the comments show on their lines as GitHub has them. When GitHub refuses it or it was not sent, the popover says why and the comments are pending again. When the answer is lost, the popover offers **Open on GitHub**, **Keep as draft**, and **Send anyway**, as [Writing to GitHub](#writing-to-github) describes, and until you choose, the bar over the end of the diff says the review may have posted, with **Open Finish review**. A review another window sent, or one that may have posted before L1 Git restarted, shows in the popover the same way. **Cancel**, Escape, or a click outside closes the popover and keeps the summary, except while the review is on its way, so how it ends shows there.

When you have a review in progress on github.com, GitHub takes no second one, so the popover says how many comments it has and that L1 Git can't add to it. **Submit it as it is** submits that review with your choice and summary, and **Open it on GitHub** opens it there. Your pending comments on this computer stay as they are.

The patches of all files are read at once, up to 8 MiB together and 1 MiB for each file. A file after the first 8 MiB is read when you come to it, or near it in **All files**. **All files** draws a file of more than 3,000 lines without syntax colors. In a partial clone that lacks the files' contents, the tab lists the files without line counts and shows no diff, because L1 Git never fetches contents for a read. A partial clone that lacks folders shows no files either. In a shallow clone that lacks the commit where the pull request starts, or whose counts differ from GitHub's, it says that the commit is not there instead of showing a diff.

#### Viewed files

**Viewed** above a file, or **V**, marks it as viewed, and once more unmarks it. At the end of a file, **Mark viewed** does the same, and **Mark viewed, next file** also goes to the next file in the tree that is not viewed, and from the last one on to the first. The tree dims a viewed file, checks it, and counts how many are viewed. In **All files**, marking a file folds it and unmarking unfolds it. The arrow before its name unfolds a viewed file to look again, and it stays viewed. Marking a file whose header is pinned puts the next file at the top. Unmarking it again before you scroll goes back to where you were. Where fewer lines follow than the view holds, the view moves up instead. Merged and closed pull requests can be marked too.

A mark belongs to the pull request and to exactly this change of this file: its path, its old path when it was renamed, its blobs, and its mode, before and after. When new commits, or a base that changed in that file, change any of them, the mark drops. When the file goes back to what you viewed, the mark is there again. A rebase that leaves the change to a file alone keeps its mark.

Marks stay on this computer, in the app's local storage under `l1git.viewed.v1`. Nothing is sent to GitHub, which does not know them, and L1 Git does not read what you marked as viewed on GitHub. All who sign in to GitHub in this app share them. L1 Git keeps the marks of the 200 pull requests you marked last, up to 5,000 for each, and up to 1.5 million characters together, the newest first. The text of a mark is the first 16 digits of each blob ID, the two modes, and the paths. When the marks can't be saved, a bar says so, and they last until you quit. The marks of a newer L1 Git are left as they are, and yours last until you quit too.

### Review drafts

Words typed for a pull request and not sent yet are drafts. L1 Git saves a draft 400 ms after the last keystroke, in `drafts.json` beside `host.json` in the app's configuration folder, and never sends it anywhere by itself. Drafts survive a restart and a crash, which loses at most the last 400 ms of typing. They need no sign-in and no network. Each draft belongs to the account, the GitHub, and the pull request it was written for. A draft on lines belongs to the commit it was written against, and every other draft follows the pull request's head. The [comment box](#comment-on-lines) in **Files changed**, the summary in **Finish review**, the conversation's comment box, and each reply box keep their words as drafts.

Two windows, or two copies of L1 Git on one configuration folder, take turns with `drafts.json` through a lock on `drafts.lock` beside it, so neither saves over a change it has not read. When another window changed or deleted a draft after this window read it, this window saves nothing to that draft until you keep your words or take theirs. Deleting the draft deletes their version too.

A draft holds 1 to 65,536 characters, counted as Unicode characters, so an emoji counts as one. Text of only spaces, tabs, line breaks, and other Unicode spaces is no draft, and clearing a draft to such text deletes it. A draft over 65,536 characters is not saved, and L1 Git says so until an edit brings it under the limit. A pull request holds at most 100 drafts. L1 Git keeps drafts for at most 100 pull requests, across every account and GitHub. At either limit, the new draft is not saved, and L1 Git never deletes a draft to make room. At the limit of one pull request, L1 Git says to send or delete one of its drafts. At the limit of 100 pull requests, it says to send or delete the drafts of another pull request.

When L1 Git can't read `drafts.json`, as after a power loss that left it empty, it renames the file to `drafts.corrupt-<time>.json` in the same folder, where `<time>` is in Unix milliseconds. It then starts the drafts again and says where the old file went. It does this once for each unreadable file. A `drafts.json` that a newer L1 Git wrote is left as it is, and no draft saves until you update.

## Pull the current branch

The **Pull** menu in the toolbar and the command palette offer **Pull (Fast-forward if possible)**, **Pull (Fast-forward only)**, and **Pull (Rebase)**. Each one acts on the branch checked out in the current worktree. It fetches only that branch's upstream and then reads the branch again. A branch that is up to date or only ahead stays as it is. A branch that is behind fast-forwards, with the same checks as any fast-forward. The notice above the history then says how many commits it brought, such as `Pulled 2 commits into main.` The three modes differ only on a branch that has diverged from its upstream:

- **Pull (Fast-forward if possible)** opens the merge review for the upstream, as **Merge upstream…** does.
- **Pull (Fast-forward only)** leaves the branch as it is and shows a notice that suggests Pull (Fast-forward if possible).
- **Pull (Rebase)** runs `git rebase --merge --no-autostash --no-autosquash --no-update-refs --no-fork-point` onto the upstream's commit. Git runs as you, with your hooks.

Pull is unavailable when HEAD is detached, when the branch has no upstream on a remote, when that upstream is gone, while another write or sync runs, and while an operation is in progress in the worktree.

Pull (Rebase) refuses and changes nothing in these cases:

- HEAD moved since L1 Git read it, or the branch is no longer checked out in this worktree.
- A merge, rebase, am, cherry-pick, revert, or bisect is in progress.
- Tracked files have uncommitted changes. The refusal names them.
- The upstream of the branch changed since L1 Git read it.
- Another process holds `index.lock`, the index has skip-worktree, assume-unchanged, or intent-to-add entries, or sparse checkout is on.
- An untracked or ignored file sits at a path the rebase would write.
- The branch already contains the upstream's commit.

If Git stops the rebase on a conflict, L1 Git runs `git rebase --abort` and checks that HEAD is back at its old tip with no rebase in progress. The answer is `conflict` and names the conflicting paths. Nothing changes, and there is no Undo entry. L1 Git does not resolve rebase conflicts. Resolve them with Git, or use Pull (Fast-forward if possible) to merge instead. If the abort fails, the answer says to finish or abort the rebase with Git.

A finished rebase has an Undo entry. Undo moves the branch and its files back to the old tip, and Redo moves them to the rebased tip again. The entry keeps the old tip's commits, because the rebased branch no longer reaches them. The fetch and the fast-forward that a pull runs have no Undo entry.

## Merge into the current branch

**Merge into current branch…** in a local or remote branch's menu uses that branch as the source. The toolbar's **Branch** menu and the command palette offer **Merge selected branch into current branch…** for the sidebar branch you last selected. The worktree selector chooses the checked-out destination branch. Selecting a source does not check it out, and the destination does not need an upstream. Tags, symbolic remote HEAD aliases, and unrelated histories are unsupported. **Merge upstream…**, in the **Branch** menu and the palette, remains available for an attached local branch that has diverged from its configured upstream. Fetch and Push remain separate actions.

The review names the full source and destination refs and commit IDs. It identifies an up-to-date destination, a fast-forward, or a merge commit. An up-to-date review makes no change. For a merge commit, the review asks `git merge-tree` what the merge would do, as the cherry-pick review does. It then says `Applies cleanly.`, `Will conflict in: notes.txt. You resolve it in the app, then finish or abort.`, or `L1 Git cannot predict which paths will conflict.` A path that Git moves aside is named as `git merge` names it, such as `moved~HEAD`. The review cannot predict when `git merge-tree` cannot answer, or when that name is already taken, so `git merge` would add a suffix to it. **Start merge**, or **Fast-forward** for a fast-forward, rechecks the whole review, the prediction included. If the forecast changed since the review, Start refuses and reloads the review. Start also rechecks, for an upstream source, the tracking configuration. It requires clean tracked files, and the refusal names each changed tracked file. It also requires no other Git operation, and an ordinary index without sparse checkout, skip-worktree, assume-unchanged, or intent-to-add entries. Nonempty `branch.<name>.mergeOptions` or `pull.twohead` settings require merging with Git instead. Untracked and ignored files may remain when they do not overlap the source tree. The collision check is conservative, including case and Unicode aliases and a source path the eventual merge might omit.

**Fast-forward** moves the destination to the reviewed source without creating a merge commit. It uses Git's real index and has no Finish, Abort, or Undo action. Durable intent records the original and target commits before execution. Recovery accepts only a clean original destination or a clean destination at the reviewed source. An ambiguous result preserves the session evidence and needs external attention.

For a merge commit, Start runs `git merge --no-ff --no-commit --no-autostash --no-overwrite-ignore --no-edit <reviewed-source-oid>`. Both clean and conflicting merges stop before committing. When Start stops on conflicts, L1 Git selects the merging worktree, opens the inspector, and opens the first conflicted file in the resolver. The persistent panel identifies the session after restart. A later fetch or local edit can advance the source branch. The active merge continues with its original source commit.

Start and Abort hold the real index lock while Git uses a private index. Start records affected paths from that protected index, excluding unrelated worktree edits. The footprint is durable before index publication; Active is recorded afterward. Private execution disables hooks, then runs `post-index-change` after publication and the durable phase update. Finish retains its normal user hooks and signing. A hook or another process can add later changes, but those changes cannot expand the saved footprint.

The panel above the history reads, for example, `Merging origin/main into main`. Its progress button, such as **0 of 1 resolved**, shows the files in the inspector under **Needs resolution**, **Resolved**, **Merged cleanly**, and **Not staged**. When L1 Git cannot read which paths stopped with a conflict, one **Staged** group takes the place of **Resolved** and **Merged cleanly**. **Abort merge…** and **Finish merge** sit beside it. Supported text conflicts use the Pierre resolver, with separate **Save result** and **Mark resolved** actions. Binary files, symbolic links, files that one side deleted and the other edited, and files that only one side added get the choice of sides. Structural, filtered, and other unsupported conflicts keep their external-resolution instructions. After resolving one with Git, **Refresh conflict** in the resolver rereads it. The managed index controls apply only to the merge's affected paths. Ordinary Commit, Amend, stash, discard, checkout, and ref changes in that worktree stay unavailable.

Finish requires no unresolved paths or unstaged tracked changes, no unsaved conflict draft, a reviewed staged stamp and tree, and a message. The message fields start with Git's suggested message, marked **Suggested**. After you edit them, **Edited · Use suggested** puts the suggestion back. Finish runs Git's commit command with the user's hooks and signing settings. A merge whose tree equals its first parent's tree still creates the required two-parent commit. The result distinguishes a landed commit from an unchanged failure, including a timeout or a hook that changes the reviewed tree.

**Abort merge…** asks before discarding merge results and saved resolutions. It also names in-memory resolution drafts to discard. A draft edited after confirmation remains available. The commit message draft stays available. Before invoking Git, Abort refuses any changed tracked path outside the persisted merge footprint and names the paths to preserve. Native Git can silently discard such staged edits, so a clean status after Abort would not prove that they were safe. L1 Git uses `git merge --abort`, never hard reset or clean, and preserves unrelated untracked and ignored files.

Start, Finish, and Abort have no lifecycle Undo. While active, the worktree has a separate session journal for existing Index and Resolution changes. Undo Mark resolved restores conflict stages; Undo Save restores the previous file bytes. Finish and Abort permanently close that journal. Earlier global history remains intact, including entries in other linked worktrees. Older entries still apply their normal HEAD and content checks. A global Undo from another worktree cannot change a worktree with an active merge, and branch mutations cannot rename or move an active destination.

`mergeReview` returns the immutable review. `mergeState` returns `idle`, `active`, `attention`, or `replay`, which **A cherry-pick or revert in progress** describes. Attention distinguishes an external Git operation from managed-session recovery so existing conflict editing remains available for external operations. `merge` accepts `start` with the review, `finish` with the session ID, staged stamp, tree and message, or `abort` with the session ID. Both transports use these strict schemas. The native activity guard and existing UI draft-task guard cover every lifecycle command and its refreshes, including failed commands.

Session intent lives under the worktree's own Git directory at `l1git/merge/<session-id>/`, with a durable current pointer, retained objects, and a separate Undo store. The phases are Starting, FastForwarding, Active, Finishing with the intended tree, Aborting, and Closed with a terminal receipt. Repeated Finish or Abort returns the recorded terminal outcome without rerunning Git. Normal Active restart recovers the panel. An interrupted Starting phase with unproven path ownership, corrupt records, or incompatible Git state shows **Merge needs attention** and blocks destructive continuation. Recovery never guesses, resets files, or deletes the evidence. Preserve the session directory and resolve ambiguous states externally.

## Start a cherry-pick or revert

Two requests apply one commit to the worktree's checked-out branch. `replayReview` carries `path` and `of`, which holds the kind and the commit, and says what would happen. `write` of `replay` carries that review and does it. Both ignore replacement objects, as every L1 Git read does, and the operation runs with `diff.algorithm=histogram`, because `git merge-tree` uses that algorithm whatever your setting says, so the commit holds what the review showed. If a merge driver or another Git setting still makes the result differ, the commit stays with its Undo entry, and the answer `afterHookFailed` says so. The review names a path Git renames to avoid a clash by the name Git gives it, such as `d~1e0721a (pick me)`, and refuses an untracked or ignored file there.

**In the app.** Right-click a commit in History, or select it and open the command palette. The entries read **Cherry-pick onto main…** and **Revert on main…**, naming the active worktree's branch, or **Cherry-pick onto current branch…** and **Revert…** when it is on no branch. The active worktree is the linked worktree last selected, or else the repository root, as for a merge. The entries hold no refusal rules, so a merge commit opens the review too. They are unavailable in the menu and absent from the palette only while that worktree is not idle: a write or fetch runs, or a merge or a cherry-pick or revert is in progress.

The review dialog names the full commit ID and subject, and the destination branch and its ID. It says **Applies cleanly. L1 Git will commit it straight away, and Undo removes it.**, or **Will conflict in: …. You resolve it in the app, then finish or abort.**, or **These changes are already there, so there is nothing to apply.** with the confirm button unavailable. A refusal shows its message alone, with the button unavailable. It closes when the repository or active worktree changes, so a delayed review never opens over another worktree. **Cherry-pick** or **Revert** sends `write` with `expect.head` from the review. A clean result closes the dialog and posts a notice such as `Cherry-picked 79dadbc onto main.` or `Reverted 79dadbc on main.`, with **Undo**. A `replayStopped` answer closes the dialog with no failure notice, and the panel takes over. When the review predicted that conflict, the panel needs nothing more. Otherwise, as with a hook or signing stop, the panel also shows the answer's message and what Git printed until Finish or Abort. A `staleView` answer keeps the dialog open, says to review again, and reads the review again. Any other refusal also stays open and reads again.

**The review.** It holds `root`, `kind`, `commit`, `subject`, `destination`, which names the branch and its commit ID, and `prediction`. A prediction is `clean` with the tree Git would make, `conflict` with the paths that would conflict, or `empty` when the result equals HEAD. L1 Git gets it from `git merge-tree --write-tree`, as **Affected paths** below describes, and keeps no memo. A review writes only the loose objects `git merge-tree` makes. It leaves the index, the files, and every ref as they are, and it reads unstaged paths from `git status`, because `git diff` rewrites the index and runs `post-index-change` for a file touched with no edits, even with `GIT_OPTIONAL_LOCKS=0`.

A review refuses with `conflict`, says why, and changes nothing in these cases. An object that is not a commit answers `invalidOid` instead.

- A Git operation is in progress, or a merge session is unfinished.
- HEAD is detached, or the branch has no commit.
- The commit is a merge commit, because version 1 has no way to choose a parent.
- A cherry-pick names a commit already on the branch, or a revert names a commit not on it.
- `index.lock` exists, the index holds a skip-worktree, assume-unchanged, or intent-to-add entry, or the worktree uses sparse checkout.
- A path is staged or unmerged, and the answer names it.
- `pull.twohead` is set, because it changes what `git cherry-pick` does and `git merge-tree` ignores it.
- `git merge-tree` cannot read the commit, as when a partial clone lacks a blob.
- An unstaged edit sits on a path the result changes, and the answer names it. An unrelated unstaged edit stays.
- An untracked or ignored file sits at a path the result adds, and the answer names it. No exclude rule applies, because `git cherry-pick` overwrites an ignored file there with no warning.

**Start.** `write` of `replay` runs the same checks and compares the new review with the one it carries, field by field, so a destination that moved or a prediction that changed answers `staleView` with `headMoved`. An `empty` prediction answers `unchangedPath`. L1 Git then records the entry, with its change durable on disk, and runs `git cherry-pick <commit>` or `git revert --no-edit <commit>` as you, on the real index, with lazy fetches and no prompts. The request has no way to pass `-x`, `-m`, or `-n`. Git runs `prepare-commit-msg`, `post-commit`, `reference-transaction`, and `post-index-change`, and it does not run `pre-commit` or `commit-msg`, so those two have no effect until Finish. A failing `post-commit` does not stop the result. A cherry-pick keeps the commit's author and message, and a revert uses you and Git's `Revert "..."` message.

L1 Git proves a clean result the way it proves a `git commit`, from the ID Git printed and Git's ref trace, and a line such as `Auto-merging f.txt` before the summary does not get in the way. The entry joins the global history, reads as `Cherry-pick "subject"` or `Revert "subject"`, as a finished conflict's entry does with its message's subject, and **Undo** below describes its Undo and Redo. A repeated Start answers the same entry and runs nothing, because the undo log is its receipt.

**A start that stops.** The entry drops, HEAD stays, and Git's state decides the answer, because the exit code does not say what happened. `rerere.autoUpdate` exits 1 with nothing unresolved, and an empty revert exits 1 with no marker.

- A marker and an unresolved path answer `replayStopped` with empty `output`.
- A marker and a result with nothing unresolved answer `replayStopped`, and `output` holds what Git or the hook printed. A failing `prepare-commit-msg` hook, failing signing, and `rerere.autoUpdate` all end here.
- A marker and a staged tree equal to HEAD mean the prediction was wrong. L1 Git runs `--abort` and answers `unchangedPath`.
- No marker, on a revert with a `clean` prediction and a staged tree equal to the predicted tree, means a hook or signing stopped a clean revert, because Git writes `REVERT_HEAD` only on a conflict. L1 Git writes it with `git update-ref --no-deref REVERT_HEAD <commit>` and answers as for a pick. This is the one place L1 Git touches a marker. If a `reference-transaction` hook refuses that write, the answer is `gitFailed` and says the result stays staged with nothing in progress.
- No marker, on a revert that exited 1 with a staged tree equal to HEAD, is an empty revert. It leaves `MERGE_MSG` behind, and `--abort` refuses it, so L1 Git deletes that file and answers `unchangedPath`.
- No marker otherwise means Git refused before it merged. The answer says why, as it does for `commit`, and nothing changed.

After `replayStopped`, `mergeState` answers `replay`, and **A cherry-pick or revert in progress** applies. Finish runs the hook or signing again, and a cherry-pick keeps its author. Abort restores HEAD, the index, and the files.

**After a crash.** The next request settles the entry from Git's state, as **After a crash** below describes.

- With the entry recorded and Git not started, nothing changed, and the entry drops.
- While Git writes files, Git keeps `index.lock` and its partial state. The entry drops. Delete the lock once no Git process runs, then discard the files it rewrote.
- With the result staged and no marker yet, the worktree reads as `idle` with ordinary staged changes, and the entry drops. This window has no Abort. Unstage the changes and discard them, and unrelated edits stay. A clean revert killed in `prepare-commit-msg` ends here too, because it has no marker at that point.
- With a marker and no commit, `mergeState` answers `replay`. The entry drops at the next request that reads the global history, which Finish does first and which follows Abort.
- With the branch moved and the marker still set, `mergeState` answers `replay` with `empty` set, and Abort clears the marker and keeps the commit. Git runs `post-commit` in this state during a pick, so a kill there lands here too. The entry then offers Undo.
- With the commit made and no marker, the entry offers Undo. A clean revert reaches this state when Git is killed in `post-commit`.
- With `Landed` written and the log not saved, the entry stays and offers Undo.

A Git killed while L1 Git lives answers `gitFailed`, because the commit may have landed, and the next request settles the entry the same way.

## A cherry-pick or revert in progress

L1 Git reads one `git cherry-pick` or `git revert` in progress from Git's own state, wherever it started, and shows a panel above the history. So a pick that stopped on a conflict in a terminal can be resolved, finished, or aborted in the app, and nothing happens until you act.

**The panel.** It names the operation, the commit with its subject, and the destination branch, and says how many files still have a conflict. The inspector names both sides with their short commit IDs. The progress button, such as **0 of 1 resolved**, shows the files in the inspector, and a conflicted file opens in the resolver. In a revert, the resolver says that Incoming holds the reverse of the commit, because Base is the commit and Incoming is its parent. The message fields start with `suggestedMessage`, and after you edit them, **Edited · Use suggested** puts it back. **Finish cherry-pick** or **Finish revert** stays unavailable while a path is unresolved, a resolution draft is unsaved, the message is empty, or another write runs. It also stays unavailable while Amend is on, and the panel offers **Turn off Amend**, because the Commit box that holds that setting is hidden. A refused Finish shows why in the write notice, and the panel shows what a hook printed. **Abort cherry-pick…** or **Abort revert…** asks first and names the unsaved resolution drafts it discards. The commit message draft stays. With `empty` set the panel offers Abort and no Finish, and says the result matches HEAD. While the panel shows, the Commit box, Stash, partial staging, and the palette's commit, discard, stash, merge, branch, and tag commands are unavailable. The History commit menu has no such gate, apart from its cherry-pick and revert entries. The requests below are what the panel uses.

**What counts.** `mergeState` answers `replay` when the worktree holds exactly one of `CHERRY_PICK_HEAD` and `REVERT_HEAD`, and no other operation. L1 Git proves the marker with `git show-ref --exists`, so a branch or tag with that name does not count. It then resolves the marker to a commit with at most one parent. This works in a reftable repository and in a linked worktree, where each worktree has its own marker. These cases stay `attention` with `externalOperation`:

- A sequence of commits, which leaves `sequencer/`. `--abort` would rewind the commits already picked, and `git commit` on a middle step would not end the sequence.
- Another operation alongside, such as a bisect.
- A `-m` pick of a merge commit, because Git does not record the parent number.
- A marker whose commit was pruned. A marker does not protect its commit from `git gc --prune=now`.
- A pick on an unborn branch.
- A pick whose affected paths `git merge-tree` cannot name, as when a partial clone lacks a blob.

The panel above the history then shows `message`, which names the operation. A sequence of commits names `git cherry-pick --continue` and `--abort`, or `git revert --continue` and `--abort`. **Merge needs attention** remains the heading for recovery of a merge session.

**Affected paths.** `progress.footprint` lists the paths the operation changes. L1 Git simulates it with `git merge-tree --write-tree`, which touches neither the index nor the files, and adds what `git diff-tree` finds between HEAD and the simulated tree to the conflicted paths. A path Git renames to avoid a clash has a different label in the simulation, so L1 Git works out the name Git gives it: `foo~HEAD`, `foo~1e0721a (subject)`, or `foo~parent of 1e0721a (subject)`. The list comes only from the commit and HEAD, never from the index. If HEAD already tracks that name, Git adds a suffix such as `foo~HEAD_0`, which is outside the list. Resolving a conflict, even by deleting the file, does not shrink the list, and index edits do not widen it. `git merge-tree` runs custom merge drivers, so L1 Git runs it once for each kind, commit, and HEAD, and keeps the answer in `<git-dir>/l1git/replay/<kind>-<commit>-<head>/footprint.json`. Nothing reads that folder to learn what is in progress, and a missing or damaged file costs one more run. A staged path outside the list makes Finish and Abort refuse and name it, so you end it with Git. Abort cannot separate an edit staged at a listed path from the operation's own result, so it drops that edit, as `git cherry-pick --abort` and `git revert --abort` do. That covers an edit staged before `git revert -n` on a path the revert changes, and a file you stage at the exact name the list computes for a renamed path.

**Resolving.** Only index edits inside the affected paths pass. Every other `write` refuses with `conflict`, and a branch that is the destination of a pick in any worktree cannot be renamed, deleted, or moved. Save, Mark resolved, and their Undo use a separate history in `undo/` in that same folder, as an active merge does, so `undo` of an entry from before the operation answers `staleView` with `historyChanged`. Once Git says the operation is over, the next request deletes the folder, along with any left by an earlier operation. Deleting it yourself loses only resolution Undo. From another worktree, `undo` of an entry that changes this worktree refuses with `conflict` and names the operation in progress.

**Finish.** `write` of `finishReplay` carries `of`, which holds the kind and the commit, `staged` and `tree` from `mergeState`, and `message`. It runs `git commit -F -` with your hooks and signing. A cherry-pick keeps the picked commit's author, and a revert uses you. `suggestedMessage` is `MERGE_MSG` with only its trailing `Conflicts:` block cut, as `core.commentChar` or `core.commentString` writes it, so a real `# ...` line in the commit's body stays. Before Git runs, Finish refuses in these cases:

- With `conflict`, while a path is unmerged, a staged change is outside the affected paths, an unstaged edit is inside them, or no single cherry-pick or revert is in progress.
- With `staleView`, when a different commit is in progress or HEAD moved, `headMoved`, or when the staged files or their tree changed, `stagedChanged`.
- With `unchangedPath`, when the staged result equals HEAD. Abort ends that case.

A hook can still stop the commit, which answers `hookFailed` and leaves the operation in progress. A `pre-commit` hook that changes the staged files lands the commit and answers `afterHookFailed`, and Undo removes the commit. A repeated Finish answers the same entry and runs nothing, because the undo log is its receipt.

**Abort.** `replayAbort` carries `path`, `of`, and `head`, and answers the state after it. With nothing in progress it runs nothing and answers `idle`, so it cannot say who ended the operation. A different commit or HEAD answers `staleView`, and an operation that is not a single cherry-pick or revert answers `conflict`. L1 Git refuses a staged change outside the affected paths and names it, because `--abort` silently drops it. Then it runs `git cherry-pick --abort` or `git revert --abort` on the real index with your hooks. An unstaged edit on a resolved path makes Git refuse, which answers `conflict`, keeps the operation, and says to stage the file or undo the edit. Abort has no undo entry, because Git cannot put a conflict back. It refuses an untracked or ignored file at a path the operation changes, because `--abort` would restore that path over the file.

**Undo.** A finished operation joins the global history, so Undo removes the commit and its file changes, and Redo lands the same commit again. Undo does not reopen the conflict, because the conflict's history closed at Finish. A step refuses with `conflict` while any operation is in progress, while `.git/index.lock` exists, while the index holds a skip-worktree, assume-unchanged, or intent-to-add entry, under sparse checkout, and when an untracked or ignored file sits at a path the step creates. It refuses with `staleView` when HEAD moved, `headMoved`, or when an edit overlaps a file the step changes, `pathChanged`. In each case HEAD and the files stay as they are. Unrelated staged and unstaged edits stay too. The step runs `git read-tree -m -u`, then moves the ref with a compare-and-swap. If another process moved the ref in between, L1 Git moves the files back and says so, and if that also fails, the answer names both failures. Before a step leaves a commit unreachable, L1 Git packs it into the entry, so `git gc` cannot take what a redo needs.

**After a crash.** The entry and its recorded change exist from before Git runs. The next request that reads the global history keeps the entry when HEAD is a new commit on the same branch, with the old HEAD as its one parent and the reviewed tree, and drops it otherwise. Git's marker is not consulted, because Git moves the ref before it clears the marker. If L1 Git and Git die in that gap, `mergeState` still answers `replay` with `empty` set, Finish refuses, and Abort clears the marker and keeps the commit. The entry then settles and offers Undo. A stale `.git/index.lock` makes `mergeState` answer `lockHeld` once every conflict is resolved, as an active merge does, because `git write-tree` takes that lock. Delete the file once no Git process is running. An Abort that stopped partway finishes when you repeat it. A crash inside a step's `git read-tree` leaves Git's partial state, where the files it rewrote show as unstaged edits and a repeat refuses until they are discarded. A crash between `git read-tree` and the ref move leaves a staged inverse, and repeating the step finishes it.

## Run the browser preview

```sh
pnpm dev
```

Open <http://127.0.0.1:1422>. The browser uses the same Rust core through a development-only loopback bridge on port 9417. Adding a repository works the same as in the desktop app.

The bridge accepts JSON POST requests only from the development origin, on two routes: `/api/run` for repositories and `/api/host` for GitHub. Each request names its operation in an `op` field. A successful answer is `{"op": ..., "data": ...}` with the same `op`, and the bridge adds `"ok": true` to it. A repository error comes back as `{"ok": false, "error": ...}`. The bridge rejects an unknown operation, a missing field, or an unknown field with status 400 and a message that names the problem. It accepts every operation in the `Request` enum in `crates/git-core/src/run.rs`, the same operations as the app. `branchMerged` takes a `branch`, `{"reference": "refs/heads/<name>", "oid": ...}`, and answers whether that tip is in HEAD's history and in its upstream's, as `{"head": bool, "upstream": {"reference", "merged"}}` with `upstream` null when the branch has none or its upstream ref is gone. `fileHistory` and `blame` take an `oid` and a `file`. `fileHistory` returns each commit that changed the file, with the file's path in that commit. `blame` returns the file's text and its line ranges, each with the commit ID, author, email, time, and subject that last changed it, or `binary` or `tooLarge`. `commitDetail` and `filePatch` take a `comparison` with a `base` and a `target`. The base is `{"kind": "firstParent"}`, which means the target's first parent or the empty tree for a root commit, or `{"kind": "commit", "oid": ...}`. The target is `{"kind": "commit", "oid": ...}` or `{"kind": "worktree", "root": ...}`, a worktree of the repository compared with its files on disk. A worktree target needs a commit base. `filePatch` of two commits also takes a `from`, the file's path at the base, which is `file` itself unless the file was renamed. With it a renamed file reads as one diff, and any file reads as `rangePatches` reads it. `rangeFiles` takes a `base` and a `head` and answers what `head` changed since it forked from `base`, as `{"kind": "ready", "mergeBase", "files", "contentMissing", "shallow"}`. A file is added, deleted, modified, changed in type, or renamed, and carries its line counts, its two blob IDs and modes, and whether it is a submodule. A rename is at least 50% the same, and Git looks for renamed and edited files among at most 1,000 added and 1,000 deleted ones. `contentMissing` is true when Git could not read every file's contents, as in a partial clone. The files then have no line counts, and only renames without an edit are found. In a `shallow` clone the merge base can be older than the commit where `head` really forked, so check the counts. `rangeFiles` answers `treesMissing` in a partial clone that does not have the folders, `missing` with the commits this clone does not have, and `unrelated` when no commit is in both histories, which names a shallow clone. `rangePatches` takes the `mergeBase` and the `head` and answers each file's path and patch in the same order, from one Git process. A file's patch is limited to 1 MiB as in `filePatch`, and all of them together to 8 MiB. The file that would pass 8 MiB and those after it answer null, and so does every file when contents are missing. These reads, and `filePatch` with a `from`, do not depend on your Git configuration, read no index, and start no file system monitor. They ignore `.gitattributes` as GitHub does for its counts. Only `.git/info/attributes`, with the `diff.*` settings it names, and `.git/info/grafts` still apply. Blob IDs in their patches are whole. `filePatch` with a `from` has a deadline of 60 s, because it can look for renames in the whole range. `fetchCommits` takes a `github` repository and one or two `oids` and answers `done`, `noRemote`, or `failed` with the failure and Git's message, as [What L1 Git changes](#what-l1-git-changes) describes. `home` answers the home folder that `~` names in a typed path, or null when the core cannot find one. `overview` reads branch status and the GitHub repository that takes its pull requests, and can fetch first. That is the remote `upstream` when it is on github.com, else `origin`, else the first remote that is. `fastForward` moves branches. `lineStats` counts added and deleted lines for up to 500 commits at once, so the history reads them only for the rows on screen. `refs` returns the root, name, HEAD, branches, tags, stashes, and submodules, so the sidebar can list a repository without reading its history. `snapshot` returns the same refs with the history. `write` takes an `operation` and an `expect`, described in [What L1 Git changes](#what-l1-git-changes). `pullCheckout`, `tryPullRequest`, `updatePullRequest`, and `removePullRequest` take a `pull`, `{"github": {"owner", "repo"}, "number"}`, and its `head`, `{"reference": "refs/heads/<branch>", "oid", "from"}`, where `from` is `same` or `fork` with its `repository`, each with whether it takes your pushes as `edits`, or `gone`. `tryPullRequest` also takes a `folder`, and the other two writes take `seen`, the tip of `pr/<number>` you saw, and `updatePullRequest` takes `replace`. Each answers the pull request's copy as it is afterwards: `absent` with the folder Try would use and where pushes would go, or why they go nowhere (`noEdits`, `forkGone`, `readOnly`, or `noRemote` when no remote of the repository is the pull request's, which only Try and Update refuse), `parked` when the branch exists and no worktree has it checked out, or `ready` with that worktree and what it holds. A parked or ready copy says how `pr/<number>` stands against the head: `upToDate`, `behind`, `ahead`, `diverged`, or `unfetched` when this repository lacks the head. `undo` and `redo` take the `id` of the entry that `write` or `undoHistory` returned. A request body can be up to 4 MiB, which holds the 1 MiB patch a hunk or line write sends back after JSON escaping. A larger body answers 400 with a message that names its size and the limit. The bridge is not included in the native app. The bridge keeps undo history in `L1GIT_UNDO_DIR`, or in `l1git-undo` under the system's temporary folder when that variable is unset. `/api/host` accepts every operation in the `Request` enum in `crates/host/src/wire.rs`, and every answer and error carries the connection `status`. `pullRequests` takes a `repository`, `{"owner": ..., "repo": ...}` as a snapshot's remotes carry it, and a `list`, `open` or `recentlyMerged`. It answers up to 50 pull requests, newest change first, as `{"items": [...], "total": ...}`. `total` is GitHub's own count, so it is larger when GitHub has more or withholds some. `recentlyMerged` covers the last seven days. A row's `checks` is null when the sign-in cannot read them. `pullRequest` takes a `repository` and a `number` and answers one pull request with the commits its head and base branches are at, your role in the base repository as `viewerPermission` (`admin`, `maintain`, `write`, `triage`, `read`, or `unknown` when GitHub names none), its reviewers, checks, commits, timeline, and review threads. Each of those lists but the reviewers holds up to 100 entries beside GitHub's `total`, the newest for commits and the timeline, and a thread holds up to 50 comments. `threads` is null when GitHub runs out of time over a pull request with many of them. The host then asks once more without them. The bridge keeps `host.json` in `L1GIT_HOST_DIR`, or in `l1git-host` under the system's temporary folder, and its token in the system keychain under the service `dev.l1.git.dev-bridge`, apart from the app's. `L1GIT_HOST_VAULT=memory` keeps the token in memory instead. `L1GIT_GH` names the `gh` to run, and `L1GIT_GITHUB_API` sends GitHub requests to a loopback address, such as a fixture server. The bridge refuses to start when `L1GIT_GITHUB_API` is not loopback. To run another isolated instance, choose both ports:

```sh
L1GIT_DEV_PORT=1423 L1GIT_BRIDGE_PORT=9418 pnpm dev
```

Every read and every write has a deadline. When the deadline passes, L1 Git stops Git and every process Git started, such as a clean filter, and the request returns a `timedOut` error that names it and asks you to retry. A stopped write also says what it left behind. The inspector shows it with **Retry details**. A history read that times out shows it with **Try again**, above the last history it read or in place of a history it never read. Each deadline is about 100 times or more the read's run time on the `pnpm fixture:large` repository:

| Read or write                                                                                                  | Deadline                                                      |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `snapshot`                                                                                                     | 120 s                                                         |
| `refs`, `lineStats`, `worktreeStatus`, `worktreePatch`, `branchMerged`                                         | 30 s                                                          |
| The index refresh after `worktreeStatus`                                                                       | 30 s                                                          |
| `commitDetail`, `filePatch`                                                                                    | 20 s                                                          |
| `fileHistory`, `blame`, `rangeFiles`, `rangePatches`, `filePatch` with a `from`                                | 60 s                                                          |
| Branch status in `overview` and `fastForward`                                                                  | 60 s                                                          |
| `write` of `checkout`, and `undo` or `redo` of a checkout                                                      | 600 s, because `post-checkout` and lazy fetches run inside it |
| `write` of `stageFiles` or `unstageFiles`, `undo`, `redo`, `undoHistory`                                       | 120 s                                                         |
| `write` of `createBranch`, `renameBranch`, or `deleteBranch`                                                   | 120 s                                                         |
| `write` of `createTag` or `deleteTag`                                                                          | 120 s                                                         |
| `write` of `discard`                                                                                           | 300 s, because filters and lazy fetches run inside it         |
| `write` of a hunk or line write                                                                                | 120 s                                                         |

A deadline covers all of a read's or a write's Git commands. A write's deadline starts again once it holds its locks. Branch status is the exception. Its deadline starts again after each fetch, checkout probe, branch move, or fast-forward merge, because those commands have their own deadlines, and after waiting for another fetch or fast-forward of the same repository to finish.

A read waits for Git's error output only when it reports a failure, and then for at most 1 s after Git exits, so a filter that leaves a background process running cannot hold a read open. Each Git command runs in its own process group, so Ctrl-C or closing the terminal does not reach it directly. The native app and the development bridge stop every Git command still running when they quit, including on Ctrl-C, SIGTERM, SIGHUP, or SIGQUIT. They wait up to 1 s for a Git command that is starting to be listed, and refuse to start new ones. Then they wait up to 1 s for each write that was stopped to delete its lock and its copy of the index. A write that reaches the index after quitting began takes no lock and answers that L1 Git is quitting. Quitting can take about 3 s when a Git command is slow to start and another ignores SIGTERM. A force quit or SIGKILL skips this step. To try a short deadline, start the bridge with `L1GIT_READ_DEADLINE_MS`, which lowers each read deadline to at most that many milliseconds. It does not change write, fetch, or fast-forward deadlines.

`worktreeStatus` lists one worktree's changed paths. These are staged and unstaged edits, renames and copies, conflicts, submodules, and untracked files. Each tracked entry carries the index entries Git reported for it: `index` for an ordinary path, `index` or `original` on a rename's `side`, and the three `stages` of a conflict. A write sends these entries back as the view it acts on. `stagedStamp` is a SHA-1 of the staged side of the list, which a commit sends back. `worktreePatch` takes a `file` from that list and a `side`. `staged` diffs HEAD, or the empty tree before the first commit, against the index. `unstaged` diffs the index against the working tree, and covers untracked files. A conflicted path returns its conflict and its diff against HEAD. That diff is absent for a submodule, for a file gone from the working tree, and for a file that matches HEAD. A staged submodule change returns its gitlink diff, and an unstaged one returns the submodule's state instead of a diff. An untracked file's patch is Git's own diff of the file against nothing, so it shows what `git add` would stage, after `.gitattributes`, line-ending settings, and clean filters such as Git LFS. On macOS, Linux, and Windows, L1 Git first reads the file without following symbolic links, then checks that Git's blob ID and shown text match those bytes. If they differ, the read fails and asks you to refresh. Windows also refuses junctions and other reparse points in parent directories. A file larger than 1 MiB on disk returns its file size instead of a diff, and Git output larger than 1 MiB returns the patch size. If a required filter fails, the read returns Git's error. A file replaced by a named pipe during the read makes the read time out instead of waiting forever. Paths inside a `.git` directory are refused. L1 Git runs no Git command that writes for either read. A clean filter, such as Git LFS, can still store objects, as it would for `git diff`.

Reads run Git with optional locks off, so Git never saves the stat data it refreshes during a read. When the index caches stale stat data for a file, as after a fresh clone, a copied repository, or a build tool that touches tracked files, every read hashes that file again. So after `worktreeStatus` answers, L1 Git runs `git diff-files`, which compares stat data only. When it lists a file that the status read found unchanged, L1 Git saves fresh stat data with `git update-index --refresh`, as `git status` in a terminal does. It creates `index.lock` itself, runs Git on a private copy of the index as a write does, and renames the copy over the index only when Git changed it. The refresh changes no index entry, flag, or file. It records no Undo entry and runs no hook, so `post-index-change` does not run, though it runs after a terminal `git status` that saves stat data. It marks no entry assume-unchanged under `core.ignoreStat=true`, and it changes only the index of the worktree that was read. The refresh never makes anything wait. It is skipped when a write, undo, redo, or ref move of the repository runs or waits, or when another process holds `index.lock`, and the next status read tries again. A write that starts waiting stops a running refresh. A terminal Git command that writes the index while a refresh runs fails as it does during any Git write, because `index.lock` exists.

An untracked file's patch differs from `git add -N` followed by `git diff` in these cases:

- Git reads `.gitattributes` from the working tree. A `.gitattributes` file deleted from the working tree but still in the index is ignored.
- A clean filter whose output changes between runs always fails with the refresh message.
- A top-level file named `-` reaches Git as `./-`, so a filter that uses `%f` sees `./-`.
- The size check runs first, so a required filter that fails on a file over 1 MiB returns the size instead of the error.
- External diff drivers and `diff.mnemonicPrefix` do not apply, as for every other diff in L1 Git.

Recents belong to each browser origin or the native WebView. The native app and browser preview have separate saved lists.

## What L1 Git changes

Repository synchronization uses these Git commands:

- `git fetch --prune --no-prune-tags <remote>` for each remote that does not set `skipFetchAll` or `skipDefaultUpdate`, when L1 Git fetches every remote. It updates only remote-tracking refs under `refs/remotes/`, and it removes those whose branch was deleted on the remote. Git 2.48 and later can also create `refs/remotes/<remote>/HEAD`. It does not write `FETCH_HEAD`.
- `git fetch --no-prune-tags <remote> <branch>` for **Fetch** of one branch. It does not prune, so the other remote-tracking branches stay as they were, and it does not write `FETCH_HEAD`.
- `git -c remote.<remote>.followRemoteHEAD=never -c fetch.bundleURI= fetch --no-tags --no-prune --no-prune-tags --refmap= --no-write-fetch-head --no-auto-maintenance --recurse-submodules=no --end-of-options <remote> <commit>...` for one or two commits by ID, only when `fetchCommits` asks for them, which only [**Files changed**](#files-changed) of a pull request does. The remote is the one whose URL is the GitHub repository that the request names, in any case. Of several it is `upstream`, then `origin`, then the first. The command adds objects and creates, moves, and deletes no branch, remote-tracking ref, tag, or other ref, whatever the remote's configuration says, and it does not write `FETCH_HEAD`. No ref keeps the commits, so Git can remove them again when it collects garbage.
- A dry-run `git fetch . <commit>:<branch>` that asks Git whether a branch is checked out in any worktree. It writes nothing. It runs only when some worktree has a detached HEAD, as a rebase or bisect leaves it. L1 Git does not move a branch when this check cannot answer.
- `git update-ref` to move a branch that is not checked out. The branch moves only from the commit you saw to the upstream commit you saw.
- `git merge --ff-only` inside the worktree of a checked-out branch. It runs only when that worktree has no uncommitted changes to tracked files and no merge, rebase, am, cherry-pick, revert, or bisect in progress. Git refuses it when the update would overwrite an untracked file.

A pull request's copy is the local branch `pr/<number>`, checked out in a linked worktree of its own. L1 Git keeps it with these Git commands, and none of them records an undo entry, runs a hook, or starts a file system monitor, because a hook or a monitor that config points into the copy may run the pull request's code before you chose to run it. Reads of the copy start no monitor either. Each command sets `core.hooksPath` on its command line to a new empty folder in your temporary folder, which outranks the repository's config, and turns off each hook that config defines by name:

- `git fetch --no-prune-tags <remote> refs/heads/<branch>` of the head branch, for a pull request from the same repository or from a fork that takes your pushes. A fork takes them when it is yours, or when its author lets maintainers edit it and you are an admin, maintainer, or writer of the base repository, as GitHub requires. The same repository takes them when you are an admin, maintainer, or writer of it, or, when GitHub names no role, when you wrote the pull request. When it takes none, the branch still tracks the head branch, so it updates as the author pushes, and the copy says pushes go nowhere, as `readOnly`. L1 Git's Push still offers to push it, and GitHub refuses. For a fork that takes none, or one that was deleted, it fetches the head commit by ID from the base remote, as `fetchCommits` does. The fetch runs before the write, so the write never waits on the network.
- `git config` to add a remote for a fork that takes your pushes when no remote is that fork yet, as adding a remote does. Try checks the folder first, so a Try refused for its folder adds no remote and fetches nothing. It is named after the fork's owner, or `<owner>-<repo>` when a remote has that name, and its URL is the base remote's URL with the owner and repository swapped, so SSH stays SSH. L1 Git never removes it.
- `git update-ref --stdin` that creates `refs/heads/pr/<number>` at the head only if no such ref exists, then `git config` for `branch.pr/<number>.remote` and `merge`. The branch tracks the head branch on its remote, or `refs/pull/<number>/head` on the base remote, which GitHub keeps after a fork is deleted and which takes no push. Push then says so instead of offering to publish the branch. A plain `git push` from the worktree in a terminal refuses under Git's default `push.default=simple`, because the branch's name differs from its upstream's. L1 Git's Push names the destination, so it works.
- `git worktree add <folder> pr/<number>`, run as you. A `pr/<number>` that exists already is checked out at its own tip. When Git fails to make the worktree, L1 Git deletes the branch it made, or puts back the settings of the branch it found.
- `git merge --ff-only` in that worktree when the author pushed, and `git reset --keep` there when you replace a branch that the author rewrote or that has commits of yours. Each runs only while the branch is still at the tip you saw. Git refuses either one rather than overwrite an uncommitted change or an untracked file at a path the pull request adds, and L1 Git names those files. Before `reset --keep`, L1 Git also refuses, and names the files, when you staged changes there or when an ignored file sits at a path the pull request changes, inside it, or where it puts a folder, because the reset would lose either one. Both keep other untracked files. A `pr/<number>` that no worktree has checked out moves by `git update-ref` from the tip you saw.
- `git worktree remove`, never forced, run from the main worktree, or from the worktree you have open when the main one is a bare repository, with the same refusals as **Remove worktree**. Then `git update-ref -d` with the tip you saw, and `git config --remove-section branch.pr/<number>`, only when the head holds every commit on the branch. Otherwise the branch stays. Remove first fetches the head commit by ID from the base remote, as `fetchCommits` does, so a push by the author since you last fetched still counts. It gives that fetch at most 15 s, not the 300 s of other fetches, and the 15 s include waiting for another fetch of the repository to finish and for a free network slot, so a remote that does not answer, or a fetch still running in the background, delays Remove by no more. When that fetch fails or runs out of time, Remove still removes the worktree, and keeps the branch, because it cannot tell whether the branch holds commits of yours. Once the worktree is gone, Remove answers the copy as it is: when Git then fails to delete the branch, Remove answers it kept rather than an error.

The lazy `conflictFile` request reads bounded base, current, incoming and working text with an opaque freshness stamp. Routine patch refreshes do not carry these texts. `saveConflict` uses the existing serialized `write` request. It records private before and after byte copies before placement. Result text is omitted from applied-operation metadata and history responses. After interruption, recovery confirms exact after bytes, drops an entry that still has exact before bytes, and retains evidence when neither matches. A post-placement error reports that the result was placed and recovery is pending. An external edit blocks Undo and Redo. Save shares the existing final filesystem check-to-rename race limit with discard.

It also writes the index of one worktree, through the `write` request:

- `stageFiles` runs `git add` for each entry's paths. It stages what is on disk, and it marks a conflicted path resolved. Staging an unstaged rename stages both of its paths.
- `unstageFiles` runs `git reset` for each entry's paths. That puts HEAD's version back in the index, or removes the path before the first commit. Unstaging a staged rename restores both of its paths. A conflicted path is refused, because `git reset` would keep HEAD's version without a word.

Paths always reach Git as literal names, so `*` and `[x]` match only themselves. L1 Git does not stage a nested repository. A name that is not valid UTF-8 reaches the app with U+FFFD in place of its bad bytes, in `worktreeStatus` and in a refusal's `paths`. A write answers `unsupportedPath` for a chosen name that such a name reads as, and so also for a valid name beside it that reads the same, because L1 Git cannot tell which one you chose.

A write changes only the paths its entries name. L1 Git reads the whole index before and after Git runs, and if Git changed any other path, the write answers `staleView` with reason `pathNotChosen`, lists those paths in `paths`, and changes nothing. That happens when a folder replaced a file or a file replaced a folder, because Git would also add or remove the paths on the other side, such as `z/x` when you stage the deleted file `z`, or `z` when you stage `z/x`. Choose both entries to stage or unstage them together. In a repository that ignores case, as macOS repositories do by default, Git stages a new file under the spelling the index already uses for its folder. So after you rename the folder `Dir` to `dir` on disk, staging `dir/b` would stage `Dir/b`. Then the write answers `unsupportedPath`, names both spellings, and changes nothing. That answer lists no other path Git would also change, so once the names match, the next try can answer `pathNotChosen` for those.

It also discards unstaged changes in one worktree, through the same request:

- `discard` puts each tracked entry's path back to its index version and deletes each untracked file. Git first writes the index version of every tracked path into a scratch folder, `.git/l1git-discard.<pid>`, with `git checkout-index`, so smudge filters, line endings, symlinks, and executable bits apply as in a checkout, and a partial clone fetches the blobs it needs. Then L1 Git copies what each path holds into the undo history, and only after that renames each scratch file over its path or deletes the untracked file. A failing filter or fetch therefore changes no file. Afterwards L1 Git writes each tracked path's index entry again without its stat data and runs `git add --refresh`, which compares the file's content with the entry and records the file's new stat data, so the next status read does not rerun its clean filters. `git add --refresh` alone keeps an entry whose recorded size differs from the file, as after a checkout that converts line endings, and Git would then show the file modified with an empty diff. Redo refreshes the index the same way. The refresh leaves every index flag as it was. It skips an entry marked skip-worktree or assume-unchanged, whose stat data Git never reads, and writes the others with `core.ignoreStat=false`. Under `core.ignoreStat=true`, `git restore` marks each file it puts back assume-unchanged, so a later edit no longer shows. After a discard, a later edit still shows.
- It refuses a submodule, a nested repository, a path below a folder that holds a `.git`, a file added with `git add -N`, a conflict, and a path that is a folder on disk or sits below a file or a symlink. `git restore` would empty an intent-to-add file and delete a folder's untracked files, so L1 Git never runs it. It also refuses two names for one file on a case-insensitive disk, whether you chose both or one is a tracked file under another spelling. Git lists such a spelling as untracked when `core.ignorecase=false` and `README.md` sits on disk as `readme.md`, and with either setting when only a letter outside ASCII differs, as for `Ärende.txt` and `ärende.txt`, because Git folds only ASCII. It does the same when only the Unicode normalization differs, as when `café.txt` is tracked decomposed and `core.precomposeunicode=true` shows it composed. L1 Git folds every name in the index with Unicode case folding and canonical decomposition, and refuses when a name that folds like a chosen path is the same file on disk by device and inode, whatever `core.ignorecase` says.
- A hard link is not kept. Discarding one name gives it a new file, so the file's other names keep the old bytes, and undo puts the bytes back as a file with one link.

It also stages, unstages, and discards part of one file, through the same request:

- `stageHunk`, `unstageHunk`, and `discardHunk` take `{"path", "hunk", "shown"}`. `hunk` counts from 0 in the patch's order.
- `stageLines`, `unstageLines`, and `discardLines` take `{"path", "lines", "shown"}`. Each line is `{"side": "deletions", "line": n}`, the old file's line `n`, or `{"side": "additions", "line": n}`, the new file's line `n`. A line of context is ignored, and a line that is in no hunk is refused with `unchangedPath`.
- `shown` is the `patch` text of the `worktreePatch` you acted on: the `unstaged` side for a stage or a discard, and the `staged` side for an unstage.
- L1 Git reads that side again through the same code `worktreePatch` uses, while it holds `index.lock`, and answers `staleView` with reason `pathChanged` and "This file changed. Refresh to see its current diff." unless its text equals `shown`. `git apply` applies a hunk wherever its context matches, even 27 lines away, and ignores the blob IDs in the patch, so without this check a stale view would stage, unstage, or discard a different spot.
- L1 Git builds the partial patch from Git's own bytes, never from the text, so a file that is not UTF-8 keeps its bytes. A picked change stays a change. An unpicked change on the side the patch applies to becomes context, and one on the other side is left out. Within a run of changes, the patch pairs each deletion with the addition beside it, as the **Split** view draws them, so a staged line lands in place of the line it replaces. A hunk left with no change is dropped, and each hunk's line numbers are counted again. The patch drops mode, rename, similarity, and dissimilarity lines, so a hunk write changes content only and a mode change stays where it was. A copy is refused, as the list below says. A creation or a deletion that keeps lines on both sides becomes an edit.
- A stage runs `git apply --cached`, and an unstage runs `git apply --cached --reverse`, on the private copy of the index. Each runs with `--whitespace=nowarn`, so `apply.whitespace=fix` cannot strip the spaces you staged and `apply.whitespace=error` cannot refuse them, and never with `--recount` or `-C`. An untracked file stages from the patch that creates it, with no `git add -N`, so looking at its diff never changes the index. An unstage hunk on a staged rename changes only the new name's entry, so the rename stays staged. `git apply` writes the entry anew, so L1 Git puts back a skip-worktree bit the entry had, and drops an assume-unchanged bit, as `git reset` does.
- A discard works out the file's new content before it touches the file. In a scratch index, `.git/l1git-partial-index.<pid>`, with its own object folder, `.git/l1git-partial-objects.<pid>`, L1 Git puts the path's index entry, applies the whole patch you saw to get exactly the content Git compared, applies the partial patch in reverse, and checks the result out with `git checkout-index` into the discard's scratch folder. Smudge filters and line endings apply as `git apply --reverse` on the file would apply them. Nothing is written into the repository's object store, and no Git command reads the file itself. Then the discard copies the file into the undo history and renames the result over it, as a whole-file discard does, after checking that the file has the device, inode, size, mode, and times it had before L1 Git read the patch. The file keeps its permission bits. Discarding the only hunk of an untracked file deletes it, and discarding some of its lines leaves it untracked.
- These writes refuse with `unsupportedPath` a binary file, a patch over 1 MiB, a conflict, a submodule, a symbolic link, a type change, a copy, and a rename that `git add -N` started. A discard also refuses a file added with `git add -N`. A pick that would put a line after one with no newline at the end of the file is refused too, because `git apply` would join the two lines. Pick the change to that last line as well.
- In a repository that ignores case, `git add` files a new path under the folder spelling the index already uses, and `git apply` does not. A stage that would create an entry under a second spelling of a folder answers `unsupportedPath` and changes nothing.
- Discarding part of a file whose line-ending rules convert it rewrites the endings of the lines it keeps, as Git does. Under `core.autocrlf=true`, a file with LF endings comes back with CRLF on every line, as after `git checkout -p`. An untracked CRLF file under `* text=auto` comes back as after `git apply --reverse`. A `.gitattributes` file deleted from disk but still in the index is ignored by a hunk discard, as by `git apply --reverse`, and followed by a whole-file discard, as by `git checkout`.

It also commits in one worktree, through the same request:

- `commit` runs `git commit -F -` with the message on standard input.
- `amend` runs `git commit --amend -F -`. It keeps the parents and the author of HEAD's commit.
- `editMessage` runs `git commit --amend --only --allow-empty -F -`, which replaces only the message and leaves staged files staged.

It also creates, renames, and deletes local branches, through the same request:

- `createBranch` carries a `name` and `at`, where the branch starts: `{"kind": "commit", "oid"}`, `{"kind": "local", "reference", "oid"}`, or `{"kind": "remote", "reference", "oid"}`. It runs one `git update-ref --stdin` transaction that creates `refs/heads/<name>` only if no such ref exists and, for a branch start, checks that the start still points at `oid`. It then writes the upstream `git branch` would write, as `branch.<name>.remote`, `merge`, and `rebase`, following Git's `setup_tracking`. Under `branch.autoSetupMerge` `true`, the default, a start that a remote's fetch refspec maps gets that remote and the ref it maps from. `simple` does that only when the ref has the new branch's name, `always` also tracks a local start through the remote `.`, `inherit` copies a local start's `remote` and every `merge`, and `false` sets none. A commit start gets none. `branch.autoSetupRebase` adds `rebase = true` as Git does. Where Git would create the branch and then fail to track it, because more than one remote's refspec maps the start or `inherit` would copy several merges while asked to rebase, the create refuses before Git runs.
- `renameBranch` carries the `branch` you saw, `{"reference", "oid"}`, and the new name `to`. It runs `git branch -m`, which moves the ref, its reflog, its `branch.<name>.*` settings, and the HEAD of every worktree that has it checked out. It never writes a create and a delete, which would leave HEAD on the old name.
- `deleteBranch` carries the `branch` you saw. It runs `git update-ref -d` with the tip you saw as the old value, then `git config --remove-section branch.<name>`.

A new name must pass `git check-ref-format --branch` and print back unchanged, so `@{-1}` is refused, and it cannot start with `refs/`. Under `core.precomposeunicode` on macOS, Git composes the decomposed characters of every name it reads from its command line, so `git branch` stores a decomposed name composed. L1 Git asks Git for that form first, then creates, compares, and records the name as Git stores it. A refused name answers `invalidRef` with Git's reason. So does a name that another branch holds, a name that would sit beside a branch as a file beside a folder, such as `feat` beside `feat/x`, and, where refs fold case, a name or a folder that differs from a branch's only in case, such as `Grp/x` beside `grp/leaf`. Refs fold case when the repository keeps refs as files and either `core.ignorecase` is true or the disk folds case, which a repository copied from another disk can leave unrecorded. Reftable keeps names apart by case, as Git does there. Where refs fold case, a rename that changes only case is refused too, because Git could not rename it back, and the reason says to rename through another name. A rename refuses a target name whose `branch.<name>.*` settings are still in the config, because Git would merge them into the moved branch and undo could not split them. It also refuses to rename a branch whose name Git would not accept back on undo, such as one that starts with `-`. Delete and rename refuse a symbolic branch, because `git update-ref` would change the branch it points at. Delete refuses with `conflict` a branch that any worktree has checked out, including a prunable or locked worktree, or that a worktree is rebasing or bisecting, as `git branch -d` does. Create refuses a name that a worktree waits on for its first commit. Names reach `git branch` after `--`, so a branch named like an option stays a name. Branch writes take no index lock and run as you, so `reference-transaction` hooks run. L1 Git passes the reflog message to `git update-ref -m`: `branch: Created from <start>` for a create, where `<start>` is the start branch's full ref, such as `refs/remotes/origin/main`, or the commit ID, `l1git undo` or `l1git redo` when an undo or redo creates a branch again, and `branch: Deleted by L1 Git` for every delete, an undo or redo that deletes included. A rename and its undo and redo write the entry `git branch -m` writes.

It also creates and deletes tags, through the same request:

- `createTag` carries a `name`, the commit `at`, and a `message` or `null`. A message of only whitespace counts as `null`. An `at` that is not a commit, such as a tree, a blob, or a tag object, answers `invalidOid`. With no message it runs one `git update-ref --stdin` transaction that creates `refs/tags/<name>` at the commit, with no old value. With a message it runs `git tag -F - -- <name> <commit>` with the message on standard input, which makes an annotated tag, as `git commit` runs: with your environment apart from inherited `GIT_*` variables, `LC_MESSAGES=C`, and your hooks. So `tag.gpgSign`, `tag.forceSignAnnotated`, your identity, and Git's message cleanup apply, and a missing identity answers `missingIdentity`. When `tag.gpgSign` is on, a tag with no message is refused with `invalidRef`, because `git tag` would sign it and needs a message to do so.
- `deleteTag` carries the `tag` you saw, `{"reference", "oid"}`, where `oid` is what the ref holds: the commit for a lightweight tag, or the tag object for an annotated one. The `refs` read gives it as each tag's `object`, beside `annotated`, which is true only when `object` is a tag object made under that tag's name. So `latest`, made by `git tag latest v1.0`, reads as lightweight though it holds `v1.0`'s tag object. It runs `git update-ref -d` with that value as the old value.

A tag name must pass `git check-ref-format refs/tags/<name>`, and it cannot start with `-` or be `HEAD`, which `git tag` also refuses. A decomposed name is composed as for a branch. A refused name answers `invalidRef` with `'<name>' is not a valid tag name.` So does a name another tag holds, a name that would sit beside another tag's folder, and, where refs storage folds case, a name or folder that differs from another tag's only by case. Deleting a tag that no longer holds what you saw answers `tagChanged`. A symbolic tag is refused.

It also saves, applies, pops, and drops stashes in one worktree, through the same request:

- `stashPush` carries `message`, `untracked`, and `paths`. An empty `message` omits `-m`, so Git writes its `WIP on …` text. An empty `paths` list stashes every local change. Each named path is sent as `:(literal)<path>`, so a name such as `x*` stays that one file. `untracked` true passes `-u`. The command is `git stash push -q`, run as you, with your hooks. `GIT_REFLOG_ACTION` stays unset, so the stash reflog keeps Git's own message.
- `stashApply` and `stashPop` carry the stash you saw, `{"name", "oid"}`, where `name` is `stash@{n}`. Both run `git stash apply -q --index <oid>`. In a partial clone that command fetches the blobs it needs, with prompts turned off. Pop then runs `git stash drop` on the `stash@{n}` that still holds that object ID, and only when Git prints that full ID. Apply leaves the entry listed.
- `stashDrop` carries the same stash. It runs `git stash drop` without `-q` and requires Git to print that entry's full object ID. Drop takes no index lock and does not read HEAD.

A push, an apply, or a pop refuses with `staleView` and `headMoved` when HEAD is not the one `expect` names. A `stash@{n}` that no longer holds the object ID you saw answers `stashChanged`. A repository with no commits yet answers `gitFailed` with `You do not have the initial commit yet` for a push, an apply, and a pop. When nothing would change, a push answers `unchangedPath` with `No local changes to save` and records no entry. When Git leaves unmerged paths, the answer is `conflict`, those paths are named, and a pop keeps the entry. A push that Git stores and then cannot finish, such as a file it cannot write, keeps the undo entry, and the answer carries Git's message. Undo restores the captured file bytes and the index rows. Redo of a push runs `git stash store` of that same commit and puts the recorded bytes back. Undo of a drop or a pop stores that commit again, so the entry returns at `stash@{0}`, which is what the notice says. A drop or a pop finds the entry at its current `stash@{n}` and checks the object ID Git prints.

`git stash push -u` deletes empty untracked folders, and neither pop nor undo brings them back. Undo of an apply that created folders leaves those folders empty. A directory rename in HEAD can make apply place a file outside the paths L1 Git captured, and that write answers `raced` with no undo entry. A crash while Git runs a push, an apply, or a pop keeps an undo entry only when the next read can name exactly what to put back. Another process that writes the index in the few milliseconds before Git reads it can be recorded as this write. A conflicted apply can leave `MERGE_RR` from `rerere`, and undo does not clear that file. L1 Git has no stash of staged changes alone. Applying an entry that was already dropped answers `stashChanged`. When no worktree row is selected, apply and pop change the worktree that has the branch named in the stash message checked out, when one worktree has it, and otherwise the repository you added. A clean worktree has no row, so that is how a stash returns to the worktree it came from.

It also checks out a branch or a commit in one worktree, through the same request:

- `checkout` carries a `target`, in the shape of `createBranch`'s `at`: `{"kind": "local", "reference", "oid"}`, `{"kind": "remote", "reference", "oid"}`, or `{"kind": "commit", "oid"}`. A local branch runs `git switch <name>`. A commit runs `git switch --detach <oid>`, which detaches HEAD.
- A remote-tracking branch checks out the local branch its remote's fetch refspec maps it to, so `refs/remotes/origin/feat/x` becomes `feat/x`. If that branch exists, L1 Git checks it out at its current tip. Otherwise it runs `git switch -c <name> --track <remote branch>`, which creates the branch and writes its upstream. A ref that no remote's refspec maps, that a negative refspec such as `^refs/heads/tmp/*` excludes, or that more than one remote maps answers `invalidRef`, because Git would change the files and only then fail to set the upstream.

A checkout refuses with `staleView` when HEAD is not the one `expect` names, `headMoved`, or when the target is no longer at the commit it names, `branchChanged`. It refuses with `conflict` while a merge, rebase, cherry-pick, revert, am, or bisect is unfinished, though Git itself only warns about a bisect, while a path is unmerged, and when another worktree has the branch checked out. It refuses with `unsupportedPath` when HEAD has no commit yet, because no `git switch` puts a branch with no commits back. Git carries uncommitted changes when it can, as in a terminal. When it cannot, because the checkout would overwrite a change, an untracked file, or an ignored file, Git refuses and changes nothing, and the answer is `conflict` with Git's reason and the paths, ten at most and then how many more. L1 Git never stashes for you. Git runs with `--no-overwrite-ignore`, so it never replaces an ignored file, such as an `.env` the target commits, which no undo could bring back. Before Git runs, L1 Git also refuses with `conflict` a change the target already holds: a staged change equal to the target's version, or a file you deleted that the target changes or deletes. A file you renamed and added with `git add -N` counts as deleted under its old name. Git would fold such a change into the checkout, so it would no longer show as a change, and switching back would lose it. In a sparse checkout, Git does not refuse an untracked or ignored file where the target adds one. It takes the file over, and switching back deletes it. So in a sparse checkout L1 Git refuses with `conflict` and names those files.

Git runs `git switch --quiet` as it runs `git commit`: with your environment apart from inherited `GIT_*` variables, with `LC_MESSAGES=C`, and with your hooks, so `post-checkout` and `reference-transaction` run. `GIT_REFLOG_ACTION` stays unset, so HEAD's reflog reads `checkout: moving from main to feat/x`, which `git switch -` reads. In a partial clone, Git fetches the blobs the target needs, with prompts turned off, so a remote that asks for a password fails the checkout. That fetch runs under the write lock and the write deadline, and it does not count against the four fetches at once. With `submodule.recurse` set, Git also updates submodules, and an undo leaves their HEADs detached at the commits the superproject records. After `git merge --squash`, `git switch` deletes `SQUASH_MSG`, and an undo does not bring it back.

L1 Git reads where HEAD went once Git exits, whatever Git's exit. When HEAD reached the target, the write keeps its entry. If `post-checkout` then failed, the answer is `afterHookFailed`, with what Git and the hook printed in `output`, and the entry stays, so Undo puts HEAD back. If the target branch moved in the instant between L1 Git's check and Git's read, HEAD is on that branch at its new tip, and the answer is `raced` with the entry kept. If HEAD moved anywhere else, the answer is `raced` with no entry. Git writes the index and the files before it moves HEAD, so a held `.git/HEAD.lock` or a `reference-transaction` hook that refuses the move leaves the files at the target and HEAD where it was. When L1 Git sees that the index changed and HEAD did not move, it puts the files back with `git read-tree -m -u <target> <HEAD>`, which keeps the changes Git carried, deletes a branch that `git switch -c` created, puts that branch's settings back, and answers with Git's reason and that nothing changed. When it cannot put them back, the answer says so, and the target's changes show as staged changes beside yours. Unstage the files that the target changes, then discard them. When the deadline stops Git after HEAD moved, which a `post-checkout` hook that does not finish can cause, the answer is `timedOut`, and the entry stays, so Undo puts HEAD back. When Git cannot write a file, such as one in a folder you cannot write to, it prints an error, still moves HEAD, and exits 0. L1 Git answers as it does for any checkout, without a warning. Those files show as changes, and Undo refuses until you put them right.

L1 Git runs at most one fetch, push, or fast-forward at a time per repository, and at most four network operations at once. It also runs at most one write, undo, redo, or branch move at a time per repository. Ordinary writes never wait for a fetch. Merge lifecycle commands take the fetch gate before the write lock and the cross-process history lock. Merge Finish can create a two-parent commit. Pull (Rebase) runs `git rebase` as a write, under the write lock.

### A write goes ahead only if the repository still matches what you saw

A `write` names the worktree and an `operation`, either `{"kind": "stageFiles", "entries": [...]}` or `{"kind": "unstageFiles", "entries": [...]}`. The entries are `worktreeStatus` entries, sent back unchanged with every field, `null` ones included. Its `expect` is `{"head": ...}`, the HEAD that `worktreeStatus` returned. L1 Git creates `.git/index.lock` itself, so another Git process that writes the index fails as it does during any Git write. Then it compares HEAD and each path's index entries, by mode, object ID, and stage, with what the request carries. If any of them changed, the write answers `staleView` and changes nothing. If another process holds `index.lock`, the write answers `lockHeld` and changes nothing. Git runs on a private copy of the index, `.git/l1git-index.<pid>`, which keeps the index's modification time, so Git still compares the contents of a file edited in the same second the index was written. L1 Git renames the copy over the index only after the write and its undo entry are recorded. Each command on the copy sets `core.splitIndex=false`, so Git keeps the copy whole and never creates or deletes a shared index file during a write. A write, undo, or redo that is refused leaves a split index exactly as it was. The index one puts in place is whole. With `core.splitIndex=true`, Git splits it again at its next write, and an index split only by `git update-index --split-index` stays whole. A write that changes nothing answers `unchangedPath`.

A `staleView` error carries a `reason` beside its `message`: `headMoved` when HEAD is not the one the request or the undo entry names, `pathChanged` when a path's index entries differ from it, for a discard and its undo and redo when a file on disk differs, or for a hunk or line write when the patch differs from `shown`, `pathNotChosen` when Git would also change a path the request does not name, with those paths in `paths`, and `historyChanged` when an `undo` or `redo` names an entry that is not next, and `branchChanged` when a branch's tip differs from the one a branch write or a checkout names, a create's start branch included, or when a branch or the worktrees that have it checked out changed since the write an `undo` or `redo` steps, and `tagChanged` when a tag no longer holds what a delete names, or holds something other than what the write left or found when an `undo` or `redo` steps it, and `stashChanged` when a `stash@{n}` no longer holds the object ID a stash write names, or no longer holds what the write left or found when an `undo` or `redo` steps it.

Writes set `GIT_EDITOR=:`, so no write opens an editor. They set `GIT_REFLOG_ACTION` to `l1git stage`, `l1git unstage`, `l1git discard`, `l1git stage part`, `l1git unstage part`, `l1git discard part`, `l1git undo`, or `l1git redo`. Staging and unstaging commit nothing, so no commit hook runs and nothing is signed. Git runs no hook while it changes the private copy. Each of its commands sets `core.hooksPath=/dev/null` and turns off, by name, each hook that config defines for `post-index-change`, through `--config-env`, so a name that holds `=` stays whole. After L1 Git replaces the index and lets go of its locks, it runs `post-index-change` once with `git hook run`, from the worktree root and against the real index, when you have a hook file or a config hook for it. Its first argument is `1` after a discard of a file or of part of one, which changed files on disk, and `0` otherwise. Its second is `1` when the write or the restore touched an entry with the skip-worktree bit, and `0` otherwise. A write that fails or changes nothing runs no hook. A discard that stops partway publishes the refreshed index for the files it discarded, but it answers with an error, so it runs no hook. An undo of a discard writes only files and leaves the index as it is, so it runs no hook either. A redo of a discard refreshes the index and runs the hook with `1`. L1 Git ignores how the hook ends, as Git does.

### A commit goes ahead only if HEAD and the staged files still match

`commit` and `amend` carry the `message` and `staged`, the `stagedStamp` the box showed. `editMessage` carries the `message` only. L1 Git refuses with `conflict` while a merge, rebase, cherry-pick, revert, or am is unfinished, or while a path is unmerged, because an undo could not put that state back. A bisect does not stop a commit. During a single cherry-pick or revert, the `conflict` comes from the check described under **A cherry-pick or revert in progress**, and `finishReplay` is the one way to commit its result. A reftable repository keeps an unfinished cherry-pick or revert in its ref store instead of as a file in the Git directory, so L1 Git reads those two from the ref store. It refuses with `staleView` when the staged files or HEAD differ from what the request carries, and with `unchangedPath` when nothing is staged for `commit`. Git then commits on the index itself, as `git commit` in a terminal does, so files a `pre-commit` hook stages land in the commit. As in a terminal, Git lets go of the index while `pre-commit` runs, so a file another process stages during the hook lands in the commit.

L1 Git knows which commit its `git commit` made from Git's own ref update. Git runs with `GIT_TRACE_REFS`, which traces each finished ref update with the full commit IDs before and after it. On exit 0, Git prints the new commit's abbreviated ID, and only Git writes that output, because hooks print to stderr. Git abbreviates it so that no other object starts with it, and L1 Git goes on only while that is still true once Git exits. L1 Git's commit is the first update of the branch it checked before the commit, or of the detached HEAD, to the one object the printed ID names. Git traces that update once it has moved the branch and before `post-commit` runs, so a hook that later sets the branch to the same commit does not hide it. A hook that writes a made-up update to another commit with the same start into the trace, and then points the branch at that commit, gets `raced` with no undo entry. The commit it replaced is that update's old ID, which Git checked under its ref lock. L1 Git never takes a commit from HEAD alone or from an abbreviated ID, because another process can move or switch HEAD while Git runs, and can make a commit whose ID starts the same way. Git's ref lock covers the commit from when Git reads HEAD until it moves the branch, so another process that moves HEAD in that time, such as during a slow `pre-commit` hook, makes Git refuse, and the answer is `staleView`. Only the few milliseconds before Git reads HEAD are unguarded. When another process moved HEAD then, Git builds on or amends that process's commit instead of the one L1 Git showed. The answer is `raced`, and Undo moves the branch back to the commit Git replaced, never to one that the other process replaced. This holds for a commit, an amend, and a message edit, with or without a reflog. When the branch does not point at the new commit once Git exits, because another process moved HEAD or the branch during a hook or after Git exited, the answer is `raced` with no undo entry, and it names the commit. When Git fails or is killed, the answer is never a commit, even if Git moved the branch before it stopped. That answer says to check the history, and the commit has no undo entry. An amend or a message edit that makes HEAD's commit again, with the same message and files in the same second, answers `unchangedPath` and records nothing. L1 Git never reverts a commit by itself.

Hooks, signing, and message cleanup follow your Git config, as they do for `git commit`. Git runs with your environment, apart from inherited `GIT_*` variables, which L1 Git drops, `LC_MESSAGES=C`, so Git's messages stay in English, and `GIT_TRACE2_EVENT` and `GIT_TRACE_REFS`, which hooks inherit, so the Git commands a hook runs trace to the same files. Hooks run without a terminal, so a hook that reads `/dev/tty`, as some husky setups do, fails. A hook that runs longer than the 600 s deadline is stopped with every process it started. When `pre-commit`, `prepare-commit-msg`, `commit-msg`, or a preparing `reference-transaction` hook fails, the answer is `hookFailed`, and its `output` holds the last 64 KiB of what Git and the hook printed, starting with `…` when they printed more. L1 Git tells a hook's failure from Git's own refusals by the hook's exit in Git's trace2 events. Both traces go to a folder that L1 Git makes for each commit in the repository's undo folder. Only you can open it, and L1 Git deletes it with its files once the commit ends, so a Git process that a hook leaves running cannot write them again. A crash can leave the folder there until the next commit in that repository deletes it. `GIT_TRACE2_EVENT` overrides `trace2.eventTarget`, so a trace2 target in your Git config gets no events from L1 Git's commits or the hooks they run. When Git does not know your name and email, the answer is `missingIdentity`, with Git's advice in `output`. A signing setup that cannot run, such as `commit.gpgSign` with no `gpg`, fails with `gitFailed` and makes no commit. The reflog keeps Git's own wording, such as `commit: Update readme`.

### Journaled local writes can be undone

`write` answers with the entry it recorded, `{"id", "root", "operation"}`. `undoHistory` answers with the next entry to undo and the next to redo. `undo` and `redo` take the entry's `id`. If the id is not the next entry in that direction, the request answers `staleView`, so an undo never acts on an entry you did not see. Repeating an `undo` or `redo` that already happened answers the same entry and changes nothing.

An undo puts back the exact index entries the write replaced: conflict stages, intent-to-add entries, and skip-worktree and assume-unchanged flags. A redo puts back the exact entries the write left. Both refuse with `staleView` and change nothing when HEAD moved, when any of those paths changed since, or when putting them back would change any other path, such as a file staged since in place of a folder above them or a file staged since below them. In a repository that ignores case, Git puts a path back under the spelling the index now uses for its folder, and then the refusal names both spellings. One history covers every worktree of a repository. A write past 100 entries deletes the oldest, and a new write deletes the entries you could still redo.

A hunk or line stage or unstage is undone and redone the same way, from the one index entry it changed. A hunk or line discard is undone and redone as a whole-file discard is, from the copies of the file before and after. Its entry records the operation as sent, `shown` included, so an entry can hold up to 1 MiB of patch text, and `undoHistory` sends it back.

A discard's `write` checks what you saw the same way: HEAD, each tracked path's index entry, that an untracked path has none, and that a file you saw as deleted is still absent and any other still exists. Each entry must also be one that `git status` reports for its path now, so a request cannot name a file that Git ignores or hides with `assume-unchanged` or `skip-worktree`. Right before it renames over a path or deletes it, the discard checks again that the path's file is the one it copied, by device, inode, size, mode, and modification and change times. A path that changed stops the discard there with `staleView`. Paths it already changed stay discarded, the entry records only those, and the answer says Undo puts them back. When L1 Git cannot write that narrower record, it puts those paths back, keeps no entry, and answers that it made no change. When it cannot put them back either, it keeps the entry and answers that Undo cannot restore them, naming each file it could not put back and the copy in the undo history that holds what the file held before. An edit that lands between that last check and the rename is still lost, because a rename cannot check what it replaces. Undo of a discard checks that each path still holds exactly what the discard left, bytes, permissions, and link target, then writes back what it held before through a scratch file and a rename, creating missing folders. No filter runs, so a lossy clean filter, such as one that strips notebook outputs, or a line-ending rule cannot change the bytes it puts back. Redo checks that each path holds exactly what it held before the discard and writes back what the discard left. A path already in the target state is skipped. A path in neither state refuses the whole step with `staleView`, names the path, and changes nothing. Undo and redo check each path again right before its rename, the same way. A path that changed stops the step there with `staleView`, and the answer says that the files already put back, or already discarded again, stay that way. Undo and redo of a discard do not check HEAD or the index, because they only write files whose bytes the entry holds. They hold `index.lock` while they run, so a Git command in a terminal cannot change the same files halfway through.

Undo of a commit, an amend, or a message edit moves the branch, or a detached HEAD, from the new commit back to the one before, in one `git update-ref` transaction that refuses when the ref moved since. Redo moves it forward again. Both refuse with `staleView` when HEAD moved, and with `conflict` while a merge, rebase, cherry-pick, revert, or am is unfinished. During a single cherry-pick or revert, the history is that operation's own, so an older entry answers `staleView` with `historyChanged` instead. Undo of a first commit deletes the branch, so HEAD has no commits again. Undo moves only the ref, as `git reset --soft` does, so files you staged after the commit stay staged beside the commit's own. Undo of a finished cherry-pick or revert is the exception, because it also moves the files. When Git or a `reference-transaction` hook refuses the move, the answer says the branch did not move. Before an undo or an amend leaves a commit unreachable, L1 Git packs it into the entry, so `git gc` cannot take what a redo needs.

A branch write records, for each branch name it touches, the tip, the `branch.<name>.*` settings in file order, and the worktrees whose HEAD names it, before Git runs and again after, whatever Git's exit. A rename records both names. It keeps the entry only when undo can read what Git left as one create, delete, or rename. When another process changed the branch while Git ran, so it cannot, the write keeps no entry and answers `branchChanged`. Undo and redo compare the tip and the worktrees with what the write left, or with what it found, and refuse with `branchChanged` when either differs. They do not compare the settings. They put them back entry by entry, so a later `git push -u` on that branch does not block an undo. A key with no value reads as `true`, and undo writes it back as `true`. Undo of a create deletes the branch with the tip it made as the old value. Undo of a rename runs `git branch -m` back. Undo of a delete creates the branch again with no old value and puts its settings back. An undo or a redo that creates a branch refuses with `branchChanged` when a branch of that name exists again, whatever its tip. L1 Git cannot tell that branch from one you made, and taking it over would let the next step delete it. Before a delete, or an undo of a create, L1 Git packs into the entry every object the tip reaches that no other local branch or tag reaches. An undo of a create packs them even when the branch was already deleted outside L1 Git, as long as Git still has them, so a redo can bring the branch back. Remote-tracking refs and HEADs do not count, because a fetch with `--prune` or a checkout can drop them before you undo. A later undo copies back whatever the repository lacks, so it works after `git reflog expire --expire=now --all` and `git gc --prune=now`. Objects that another local branch or a tag also reached, which was later deleted outside L1 Git and pruned, are not in the entry, and that undo answers that Git no longer has some of the branch's commits. A deleted branch's reflog is not restored. A promisor object of a partial clone that was never fetched is skipped, because Git can fetch it again. Branches belong to the whole repository, so their undo runs from any of its worktrees, even after the worktree the write ran in is removed.

A tag write records what the tag's ref holds before Git runs and again after, whatever Git's exit, and keeps the entry only for a create or a delete. Undo of a create deletes the tag with the object it made as the old value, and redo creates it again with no old value, so the ref points at the same commit or the same tag object. Undo of a delete creates the tag again at the object it held. Before a delete, or an undo of a create, L1 Git packs into the entry the tag object, for an annotated tag, and every object it reaches that no local branch and no other tag reaches, so undo works after `git gc --prune=now` and gives back the same tag object ID. Undo and redo refuse with `tagChanged` when the tag holds something other than what the write left, or what it found. Tags belong to the whole repository, so their undo runs from any of its worktrees.

Undo of a checkout runs `git switch` back to the HEAD the checkout found, under the same rules. It refuses with `headMoved` when HEAD is not where the checkout left it, with `branchChanged` when the branch it goes back to moved since, and with `conflict` while an operation is unfinished, for a change Git would overwrite, and for a change that branch already holds. So undo goes back to `main` only while `main` is still at the commit you left. After `main` moves, check it out instead. Undo of a remote-branch checkout then deletes the branch it created, with the tip it made as the old value, and puts its `branch.<name>.*` settings back as they were before, a leftover section included. Before it switches, it refuses when that branch moved, when another worktree has it checked out, or when a rebase or bisect uses it, so a refused undo leaves HEAD where it was. Redo creates the branch again in the same `git switch -c`, so a refused redo creates nothing, and then puts its settings back. When a branch of that name exists again, whatever its tip and whether or not HEAD is on it, redo refuses with `branchChanged`, as a branch redo does. Each step first reads where HEAD and the branch are, so a stopped undo finishes on the next try. A redo stopped after Git created the branch refuses on the next try for the same reason, and the branch stays as Git left it. Before HEAD leaves a detached commit, and before undo deletes a created branch or finds it already deleted, L1 Git packs into the entry the objects that the tip reaches and no branch, tag, or remote-tracking branch reaches. Remote-tracking branches count here, unlike for a branch delete, because packing a remote branch's whole history on every checkout costs too much. So after a fetch with `--prune` drops that remote branch and `git gc --prune=now` runs, an undo or a redo can answer that Git no longer has its commits. A checkout's undo and redo run in the worktree it changed. A failed `post-checkout` during an undo or a redo answers `afterHookFailed` once the step is done.

The undo history lives outside your repository, so `git gc` there cannot delete what an undo needs, and no push can publish it. The native app keeps it in its app data folder under `undo`. Each repository gets a folder named by the SHA-1 of its Git common directory. The folder holds a `lock` file that one write at a time holds, `log.json`, and `entries/<id>/` for each entry. An entry folder holds `applied.json`, the answer `write` gave, `change.json`, the index entries or files before and after, and `objects/pack`, a Git pack of the blobs those entries name. A discard's entry holds `files/` instead, a plain copy of each file before and after the discard. Every folder of the history is readable by you alone, and each copied file is created readable by you alone, even when the undo folder itself is readable by others. `change.json` records each file's own permissions. Discarded content stays there until the entry is deleted, so a secret you discarded lives in the undo folder until 100 later writes push the entry out, or until you delete that folder. Deleting the oldest entry deletes its folder. `log.json` records the common directory's device, inode, and creation time. A repository deleted and created again at the same path has a new common directory, so it starts with an empty history, and the old entries go at its next write. L1 Git refuses to keep history in a folder that another user owns or can write.

The compiler checks part of this. Every `match` on `Operation` and on the recorded `Change` names each variant, and `write/mod.rs` denies clippy's two wildcard lints, so a new operation without a recorded `Change` does not compile, and neither does a new kind of `Change` without a restore. The compiler also gates the write runner, `git::Write`, and index publishing. Each runner needs one of the constrained transactions in `write/txn.rs` to start. The index transaction stages, unstages, and discards. Every command it starts uses its private copy as its index, and only its three commits replace the index: one after the store records a new entry, one after a discard changed the files its recorded entry holds, and one for the undo or redo of the entry the log names next. So a command on the index runner cannot reach the index before its record. The commit transaction runs only `git commit`, built from a commit kind and a message, after the store records a pending entry or the merge session records Finishing intent. It runs on the real index, with your hooks, so it is the one write that Git publishes itself. The ref transaction runs `git update-ref --stdin` with a compare-and-swap for each ref, for the undo and redo of commits and for branch writes, and `git branch` for a rename and an upstream. It takes no index lock, and `reference-transaction` hooks run as they would for `git update-ref`. It also runs `git switch` for a checkout and its undo and redo, and `git read-tree -m -u` for the undo and redo of a finished cherry-pick or revert, on the real index and with your hooks, as the commit transaction runs `git commit`. The replay transaction runs only `git cherry-pick <commit>`, `git revert --no-edit <commit>`, `git update-ref --no-deref REVERT_HEAD <commit>`, `git cherry-pick --abort`, and `git revert --abort`, the same way.

The merge index transaction admits only pinned Start and Abort commands against a private index while holding the real index lock. Finish uses the commit transaction after durable merge intent.

The refresh transaction runs only a pinned `git update-index --refresh` against a private copy while holding the real index lock. It replaces the index with no record, because that command changes only the stat data the index caches for each file.

The compiler checks nothing else. The read runner, `git::run` and `git::read`, takes any arguments, so it can run a command that writes the index or the worktree. `git::mutate` runs fetches and branch moves, and the fast-forward's `git merge --ff-only` updates the index and the worktree outside the transaction and records no undo entry. The write runner can run a command that changes the worktree, such as `git checkout-index`, which no `Change` records. The compiler does not check that a `Change` records everything its command changed, or that a restore puts it back, so a restore that does nothing compiles. For the index, the whole-index comparison refuses at run time any change a write's entries do not name. The rest is checked by review and by each write PR's audit lane, and each new kind of write is proven by its PR's undo lane.

### What a stopped write leaves behind

An index write or refresh that fails, times out, or is stopped when L1 Git quits leaves the index unchanged, and it deletes its lock and its copy of the index. A force quit or a crash inside the write or refresh can leave `.git/index.lock`. Then every Git command in that worktree reports that another Git process seems to be running. If no Git process is running, delete `.git/index.lock`. It can also leave the copy `.git/l1git-index.<pid>`, the folder `.git/l1git-intent.<pid>` that an undo of an intent-to-add entry uses, or a hunk discard's `.git/l1git-partial-index.<pid>` and `.git/l1git-partial-objects.<pid>`. L1 Git deletes them at its next write or index refresh in that worktree. A commit is different, because Git moves the branch before it lets go. A commit stopped by its deadline or by a quit after that point stays made, with no undo entry, and the answer says Git may have made it. A discard stopped partway leaves each path either as it was or as the discard leaves it, never half written, and its scratch folder `.git/l1git-discard.<pid>`, which the next write deletes. When the worktree is on another file system than its Git dir, the discard, undo, and redo copy each file beside its path as `.l1git-<entry id>-<name>` and rename it from there. A stop between the copy and the rename leaves that file. A stopped discard, undo, or redo leaves its entry next to undo or redo, so the next `write`, `undo`, or `redo` in that repository removes every such file named for the next undo or redo entry before anything else, whichever worktree it runs in. Once the first file changed, its entry stays, even when a later file fails, so Undo puts back what changed. Git writes a checkout's files first, then the index, then HEAD. A checkout that a smudge filter or a lazy fetch fails partway, or that its deadline stops before Git writes the index, can leave some files at the target while HEAD and the index stay where they were. Those files show as unstaged changes, and discarding them puts them back. When the deadline stops Git after it wrote the index and before it moved HEAD, L1 Git puts the files back, as it does for a held `HEAD.lock`. When L1 Git quits or crashes in that window, nothing puts them back, and the next request does not either. HEAD stays where it was, and the target's changes show as staged changes mixed with yours. Discard does not change a staged change, so unstage the files that the target changes, then discard them. A crash that also kills Git there can leave `.git/HEAD.lock`. Delete it once no Git process is running. A checkout stopped after Git moved HEAD keeps its entry. In the undo folder it can leave `log.json.new` and an entry folder that the log does not name, which the next write deletes.

Merge lifecycle commands can leave an active merge, an unpublished private index, or a landed commit after interruption. Their durable intent and observed Git state determine recovery, as described under [Merge into the current branch](#merge-into-the-current-branch). An interrupted private Abort cannot reopen resolution history from merge markers alone. Preserve a session that reports attention. Deleting its metadata removes the evidence needed to diagnose it.

A crash between recording a write and replacing the index leaves the entry pending in `log.json`. The next `write`, `undo`, `redo`, or `undoHistory` in that repository settles it before anything else. It keeps the entry when the index holds what the write wrote and HEAD has not moved, and drops it otherwise, so an undo never offers a write that never happened. `undoHistory` also takes the locks and settles pending work before offering an entry. A commit's entry is pending from before Git runs until L1 Git has read the new commit. A crash in that time leaves a pending entry with no recorded change, which the next request drops, so that commit has no undo entry. A started or finished cherry-pick or revert records its change before Git runs, so it never has that gap. **A cherry-pick or revert in progress** says how it settles. A pending discard is always kept, because it may have changed files before L1 Git stopped, and its entry holds the only copy of what they held. Undoing a discard that changed nothing changes nothing. A pending branch write is kept when the branch no longer matches what L1 Git found before Git ran and undo can read what it holds, and the next request records that as the write's result. So a delete stopped after Git deleted the ref keeps its entry and the objects it packed. A branch undo or redo that stopped after Git moved the ref finishes the settings on the next try. One that stopped after Git created a branch refuses on the next try with `branchChanged`, because the branch now exists. A pending tag write is kept when the tag was created or deleted, so a delete stopped after Git deleted the ref keeps its entry and the objects it packed. A pending checkout is kept only when HEAD is exactly the HEAD it asked for and, for a remote branch, the branch it created is at that commit. A crash in an `undo` or `redo` after it replaced the index leaves the log one step behind. Repeating that step finds the index already there, changes nothing, and moves the log on.

Windows CI covers CRLF text, paths with spaces and Unicode, stage, commit, discard, branch and tag creation, stash, undo, and redo. The full write suite runs on macOS and Linux. Windows refuses discard and stash operations that would need to restore a native symbolic link. Those links stay unchanged. Windows stops timed-out Git commands and their descendants forcefully, which can leave Git lock files behind.

Fetch uses your SSH agent, credential helpers, and `core.sshCommand`. It ignores `GIT_SSH_COMMAND` and other `GIT_*` environment variables. L1 Git never prompts for a password, passphrase, or host key, so a remote that needs one reports an authentication failure. A fetch from one remote that takes longer than 5 minutes stops and reports a timeout. The local reads before and after a fetch use the branch status deadline. Error messages omit credentials from URLs.

GitHub owner/repository labels come only from recognized HTTPS or SSH URLs. Displayed remote URLs omit credentials. Other hosting providers are outside this slice.
