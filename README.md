# L1 Git

L1 Git is a desktop Git client in the L1 family, built with Tauri 2, React, and TypeScript. This slice browses real local repositories. It reads branches, commit history, and commit details. Its Rust core can also fetch remotes and fast-forward local branches that are strictly behind their upstream. It can stage and unstage files from the inspector, and undo and redo each of those writes, through one guarded write path in the core. L1 Git never merges, rebases, commits, pushes, or moves a checked-out branch whose tracked files have uncommitted changes.

## Run the desktop app

Install Git 2.45 or later, Node.js 26, pnpm 10.32.1, Rust 1.93 or later, and the native Tauri build dependencies. On macOS, install Xcode and its command-line tools.

```sh
pnpm install --frozen-lockfile
pnpm tauri dev
```

If macOS selects the standalone command-line tools instead of Xcode, start with:

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer pnpm tauri dev
```

Click **+** at the top of the sidebar or press **Cmd/Ctrl+O**. Enter a path or use **Browse** to choose a directory. You can open a subfolder or symlink. L1 Git saves the canonical working-copy root and keeps linked worktrees as separate repositories. A new repository joins the end of the sidebar list. Opening a repository again keeps its place. Bare repositories return an explicit unsupported error.

L1 Git opens on your last repository and fetches every saved repository. Linked worktrees of one repository share one fetch. Click **Fetch** in the repository toolbar to fetch the open repository on demand. When some of its branches are behind their upstream and clean, the toolbar shows **Fast-forward (N)**, which moves exactly those branches. A branch checked out in a worktree with uncommitted changes, or in a worktree in the middle of a merge or rebase, is not counted. A diverged branch is never counted. In the sidebar, each repository and local branch shows how many commits it has to pull and push.

The graph shows one repository at a time, with all of its local and remote branches. The sidebar can expand any number of repositories at once, each with its own branches. Click the chevron next to a repository to show or hide its branches without changing the graph. Click a repository name to show it in the graph and expand it. The toolbar shows its name right away, and the history shows a placeholder until the first read finishes. L1 Git keeps the snapshots of the eight most recently opened repositories in memory. Returning to one of them shows its graph at once, with the commit you selected and the scroll position you left, then rereads it in the background and updates the graph if anything changed. If the selected commit is gone, the newest commit is selected. A branch you click in the sidebar takes precedence over the remembered commit. Click a branch in the sidebar to select its tip and scroll the graph to it. A branch in another repository opens that repository first. Nothing is checked out. The sidebar lists branches under **Local** and **Remote** and groups them into folders at each slash in their names, so `feat/ui/x` sits in `feat`, then `ui`. Remote branches group by remote first. Folders start closed, except the ones that hold the checked-out branch or the branch you last selected. A search opens every folder that has a match. The checked-out branch has a green background. When its folder is closed, the folder gets the green background instead. L1 Git rereads local state, including the branches of every expanded repository, whenever its window regains focus, so commits and branches you make in a terminal appear when you switch back. The open history and the branches of expanded repositories also refresh after a fetch or fast-forward moves their refs. Remote branches reflect refs already on disk, usually from your last fetch. A fetch removes remote branches that were deleted on the remote, such as a merged pull request branch. Local branches stay, and a local branch that tracked one shows that its upstream is gone.

Below **Remote**, the sidebar lists **Tags**, **Stashes**, and **Submodules** when a repository has any. Tags sort by name with numbers in numeric order, so `v1.10.0` follows `v1.9.0`. Click a tag to select its commit and scroll the graph to it, as with a branch. A tag in another repository opens that repository first. When soloed branches leave a tag's commit out of the graph, a notice says so and offers **Show all branches**. Stashes list newest first, each with its message and its `stash@{n}` name. The row leaves out the branch that Git puts first in the message, and its tooltip keeps it. Click a stash to show its changes in the inspector, compared with the commit it was made on, as `git stash show` does. The inspector names that commit as the stash's only parent. Select a changed file to open its diff. The history never lists a stash, so the graph draws no stash row. A stash in another repository opens that repository first and is selected once the repository is reread. A stash saved with `--include-untracked` shows only its tracked changes. Submodules list each path that `.gitmodules` maps, with the commit the index records for it, or the commit HEAD records while the path has a merge conflict. When a sparse checkout leaves `.gitmodules` out of the working tree, L1 Git reads it from the index. A gitlink at a path that `.gitmodules` does not name is left out, and so is a submodule whose path is not valid UTF-8. When Git cannot read the stashes or the submodules, that section is left out and the rest of the sidebar still loads. The sidebar search filters tags by name, stashes by message or name, and submodules by path. Each section opens and closes on its own. The command palette lists the open repository's tags and stashes too, and finds a stash by its message or its `stash@{n}` name.

The history contains the newest 50,000 commits reachable from local and remote branches, tags, and HEAD. If a branch tip is older than that, selecting the branch says so. Internal refs and stashes are excluded. Each row shows its branch, tag, or worktree labels to the left of the graph, then the commit message. The first label sits next to the commit's graph line and `+N` lists the rest. A worktree icon marks a branch checked out in another worktree. Each graph node shows the author's initials. Hover a node for the author's name and email. Graph connections use actual parent IDs. Dashed edges lead to parents beyond the loaded history.

Right-click the history's column headers to choose which columns follow the commit message. Right-click a commit, or press Shift+F10 or the context menu key while the history has focus, for a menu that offers **Compare with working copy** and **Pick for comparison** above the same columns. **Author** shows the author's name. **Date** shows when the commit was authored, as a relative time such as `3 days ago`. Hover a date for the full date and time. **SHA** shows the shortest commit ID prefix, at least seven characters, that no other loaded commit shares, and widens to fit the longest one. Hover it for the full ID. **Changes** shows how many lines each commit added and deleted, and is the only one on at first. Hiding **Changes** stops L1 Git from counting lines. Turning on Author, Date, or SHA narrows the commit message's minimum width so more columns fit. When the menu closes, the history scrolls sideways to show the last column you turned on if it is out of view. Press Up and Down to move through the menu, Home and End to jump to the first and last item, Space or Enter to toggle a column, and Escape to close it. The app saves your columns on this device, and every repository uses the same ones.

Select a commit to inspect its message, author, date, parents, and changed paths. Changed paths appear as a file tree with added, modified, and deleted markers. Directories start open, and single-child directory chains collapse into one row. Select a file to replace the history with its diff against the same base. Use **Unified** or **Split** to change the layout. Click **Back to history** or press Escape to return. Selecting another commit closes the diff. Binary files and patches larger than 1 MiB show a notice instead of a diff. Merge changes are compared with the first parent. Root commits use the empty tree. Renames appear as a deletion and an addition. Parent links can open details outside the loaded history. Partial clones report a read error when required objects are missing locally. L1 Git never fetches them implicitly.

Click **History** next to Unified and Split to list the commits that changed the open file, newest first. The list starts at the selected commit, or at the target of a comparison, and follows the file back through renames, as `git log --follow <commit> -- <path>` does. A row whose path differs from the open file's names the path the file had in that commit. Select a row, or Tab to the list and press Up, Down, Home, or End, to show that commit's diff for the file below the list. The diff uses the Unified or Split layout you last chose. Click **Blame** to show the file as it is in the selected commit, with a band above each run of lines naming the author, the age, the short commit ID, and the subject of the commit that last changed them. Click a band, or a line number, to select that commit in the graph. The bands are buttons, so Tab reaches them and Enter selects. A band for a commit that a hidden branch leaves out of the graph, or that is older than the loaded history, cannot be selected. Blame can name a merge commit for lines the merge itself changed, and History does not list that merge, because `git log --follow` leaves merges out. Blame names authors as the graph does, without `.mailmap`, and ignores any `blame.ignoreRevsFile` setting. Blame shows a notice instead of the file for a binary file, a file larger than 1 MiB, a submodule, a file the commit deleted, and an empty file. History and Blame need a commit, so they are off for a worktree's staged and unstaged files and for a comparison with a working copy. Escape closes the file and returns to the history with the commit still selected.

Press Cmd and click a second row on macOS, or Ctrl and click on other systems, to compare it with the selected row. The older commit is the base and the newer one the target. A worktree row is always the target, so a commit compared with it shows what changed between that commit and the files on disk, untracked files included. The list reads again whenever L1 Git rereads that worktree's status and finds a change. A file removed from the index with `git rm --cached` but still on disk reads as deleted, as `git diff <commit>` shows it. Two worktree rows cannot be compared. Choose **Compare with working copy** in a commit's menu to compare it with the open repository's own working copy, even when it has no uncommitted changes. To compare two commits from the keyboard, choose **Pick for comparison** in the first commit's menu, move to the second, and choose **Compare with** followed by the first commit's short ID. A gray pin before its message marks the picked commit. Picking another commit replaces the pick, **Clear pick** in the picked commit's menu drops it, and starting any comparison clears it. The selected row keeps its selection color and the compared row takes the plain selection color and a dashed ring around its node. The inspector heading shows both ends as short IDs and a **Swap** button that reverses the base and the target of two commits. The inspector lists each end's subject with a link that selects that commit alone, then the paths that differ. A commit compared with itself says there are no changes. Select a path to open its diff between the two ends. Click a row without the modifier, or press Escape while the history has focus, to stop comparing and keep the selected row. When a diff is open, the first Escape closes it and the second stops comparing. A compared commit that a hidden branch leaves out of the graph stays compared, as a hidden selection stays selected.

Each worktree of the open repository that has uncommitted changes gets a row directly above the commit it has checked out. The row carries the worktree's name, a dashed node, and **Uncommitted changes** with a count of each kind, such as `1 modified, 1 untracked`. A worktree with no changes gets no row. No commit moves to another lane because of a row. When no newer commit in the graph connects to the commit, the row shares the commit's lane. Otherwise the row takes a new lane to the right of the lanes that pass it. A branch pointing at the commit does not change this. Hiding a branch never hides a row, because a worktree's commit always stays in the graph. Soloing branches whose history leaves out a worktree's commit hides that row. A worktree whose commit is older than the loaded history has no row. A worktree that has no commits yet gets its row at the top, under any rule. Select the row, or reach it with the arrow keys, to list its changed paths in the inspector under **Conflicts**, **Unstaged**, and **Staged**. Shift+Down from the row selects its commit. When the row shares the commit's lane, Shift+Up from the commit returns to the row. A file with staged and unstaged edits appears in both lists. A staged rename appears under its new path, and a later edit to it appears under **Unstaged** as a change to that path. An untracked nested repository appears as one entry. Select a path to open its diff with a **Staged**, **Unstaged**, or **Conflict** tag. A staged diff compares HEAD with the index, as `git diff --cached` does, and an unstaged diff compares the index with the working tree, as `git diff` does. An untracked file shows as wholly added. A conflicted path names the conflict and shows its diff against HEAD when there is one. A submodule says what changed inside it. A pure rename says which path it came from. When Git cannot read a path, its error appears in place of the diff, and a path that changed during the read offers **Refresh**. L1 Git reads each worktree's status when the repository opens, when the window regains focus, and after a fetch moves the repository's refs. It never polls. When a reread changes the open path, its diff reloads in place. When the path left its list for another, as a stage or an unstage moves it, the diff follows it there and takes that list's tag. When no list has the path, the diff closes. When a selected worktree's changes are gone, the newest commit is selected. Search never matches a worktree row, and the Author, Date, SHA, and Changes cells of a worktree row are empty.

Stage and unstage files from the worktree's inspector. Hover a path for its **Options** button, right-click it, or focus it and press Shift+F10 or the context menu key. The menu offers **Stage** under **Unstaged**, **Unstage** under **Staged**, and **Mark resolved** under **Conflicts**. A folder's menu acts on every listed path in it. **Stage all** beside the **Unstaged** heading stages every path in that list, untracked files included, and **Unstage all** beside **Staged** unstages that list. Staging stages what is on disk, as `git add` does. Mark resolved stages the file as it is on disk, so resolve the conflict in the file first. L1 Git runs one write at a time per repository and rereads the worktree after each one, whether it worked or not. If the worktree changed since L1 Git showed it, such as a file you staged or edited in a terminal, the write changes nothing, an error notice above the history says which path changed, and the lists show the current state. When a write moves the focused row to another list, focus follows the path to its new row.

**Undo** and **Redo** in the repository toolbar undo and redo the last write, and their tooltips name it, such as `Undo Stage README.md` or `Redo Stage 3 files in src`. Press Cmd+Z on macOS or Ctrl+Z elsewhere to undo, and Cmd+Shift+Z or Ctrl+Shift+Z to redo. The shortcuts do nothing while a text field has focus, such as the sidebar filter, history search, or the command palette, so those fields keep their own undo, and they do nothing while a dialog is open. After an undo, a notice names it, such as `Undid Stage README.md`, with a **Redo** button. After a redo, it names that with an **Undo** button. One history covers every worktree of a repository and survives a restart. Undo goes in order. When HEAD moved after a write, or a path it touched changed since, L1 Git cannot put the index back exactly, so the undo changes nothing and the notice says why. The older entries wait behind that one until it can be undone, for example once HEAD is back where it was.

Click a commit or Tab to the history to move through it with the keyboard. The history is one Tab stop. While it has focus, the selected row takes an accent tint, and it returns to the plain selection color when focus moves elsewhere. Press Down or J to select the next commit and Up or K to select the previous one. Press Home, Cmd/Ctrl+Home, or Cmd/Ctrl+Up to select the newest loaded commit, and End, Cmd/Ctrl+End, or Cmd/Ctrl+Down to select the oldest. On macOS, Ctrl+Up and Ctrl+Down are Mission Control shortcuts by default, so use Cmd. Press Shift+Down or Shift+J to follow the selected commit's first parent, so a move from a merge skips the branch it merged. Press Shift+Up or Shift+K to go back the way Shift+Down came. After you select a commit any other way, Shift+Up selects a newer commit whose first parent is the selected commit. When several qualify, it picks the one whose graph line runs into the selected commit, or else the nearest one. The history scrolls only as far as it must to show the selected row, and the inspector follows the selection. Press Enter to open the first changed file in the inspector's tree, and focus moves to **Back to history**. If the inspector is still reading the commit, the file opens when the read finishes. Pressing Escape, moving the selection, or leaving the history first cancels it. When the diff closes, focus returns to the history with the same commit selected, unless it is in the sidebar or a dialog. The keys work only while the history has focus, so typing in a search field or a dialog never moves the selection. A button reached with the keyboard takes a light accent tint and a 2px accent bar along its bottom edge instead of an outline. A mouse click shows neither. Text fields keep their outline.

Right-click a branch in the sidebar, or focus it and press Shift+F10 or the context menu key, to hide or solo it in the graph. **Hide** removes the commits that only that branch reaches. Commits that another branch, a tag, a worktree, or HEAD also reaches stay, so hiding a merged branch removes only its label. **Solo** shows only the soloed branches and HEAD's ancestry. Solo more branches to add their ancestry. Choosing Hide while branches are soloed, or Solo while branches are hidden, starts over with that one branch. Hover a branch for an eye icon that hides it, or, while branches are soloed, a solo icon that solos it too. A hidden branch keeps a muted eye icon and a soloed branch a blue solo icon. A closed folder or section that holds a hidden or soloed branch shows the same icon. Click the icon or choose **Show** or **Stop soloing** to undo, or choose **Show all branches** to clear every rule in that repository. Search, keyboard movement, and the branch highlight cover only the commits the graph shows. If a rule hides the selected commit, it stays selected in the inspector. Up or Down then selects the nearest commit the graph shows in that direction, or in the other direction when none is left that way. Enter and Shift+Enter in the search field step to the next or previous match after the hidden commit's place in the history. Clicking a branch whose tip the graph leaves out keeps the selection and says the branch is hidden, with a button that shows it, selects its tip, and returns focus to the history. The notice closes when you select a commit, change a rule, or open a repository. Each repository keeps its own rule, and the app saves it on this device. A rule forgets branches that no longer exist when L1 Git reads the repository's branches afresh, never from the snapshot it shows while rereading a repository you return to, so a branch you create later with the same name starts visible, and a solo rule whose branches are all gone clears.

Press Cmd+F on macOS, or Ctrl+F on other systems, to search the loaded history. A field opens above the history. It matches commits whose subject, author name, or email contains what you type, and commits whose ID starts with it. Matching ignores case and treats composed and decomposed accents alike, as the sidebar filter does. Matching rows stay lit, and the other rows and the graph lines fade. The selected row keeps its full selection color. The field reads `n of m` while the selected commit is a match, however you selected it, and the number of matches otherwise. Press Enter or Shift+Enter in the field, or click the arrow buttons beside it, to select the next or previous match after the selected commit, in history order. The history scrolls to each match. Press Escape in the field, or click the close button, to close the search. The selected commit stays selected and focus returns to the history. Opening the search closes the column menu, and opening another repository closes the search. Search reads only the loaded commits the graph shows and their subjects, not full commit messages. While a file diff is open, the shortcut does nothing in L1 Git, so click **Back to history** first.

Press Cmd+P on macOS, or Ctrl+P on other systems, to open the command palette. It lists the actions that apply where you are, the repositories in the sidebar, and the branches of the open repository. Type to filter. A title that starts with what you type comes first, then one with a word that starts with it, then one that contains it, then one that has its letters in order. When two match equally, actions come before repositories and repositories before branches. Press Up and Down to move through the list, Enter to run the highlighted item, and Escape or a click outside the palette to close it. Focus returns to where it was. When that control is gone or hidden, such as a menu the palette closed or a sidebar it hid, focus goes to the history, or to **Back to history** while a file is open. When neither is on screen, as on Settings with the sidebar hidden or while a repository opens or after it failed to open, focus goes to **Toggle sidebar**. After you open another repository from the palette, focus moves to its history once it loads, unless you clicked, typed, or moved focus elsewhere in the meantime. Opening the palette closes an open menu. An action that needs something appears only when it is there. **Fetch** and **Fast-forward** need an open repository, **Show unified diff** and **Show split diff** need an open file, and **Show file history** and **Show blame** need an open file in a commit. **Compare with working copy** and **Pick for comparison** need a selected commit. With a commit picked, **Compare with** and the picked commit's short ID compares another selected commit with it, and **Clear pick** drops the pick. **Swap compared commits** and **Stop comparing** need a comparison. **Stage all** and **Unstage all** need a selected worktree with unstaged or staged paths. **Undo** and **Redo** need an entry and carry its name, such as **Undo Stage README.md**. **Hide**, **Solo**, **Show**, and **Stop soloing** name the sidebar branch you last selected, while its tip is selected or its hidden notice shows. While the notice shows, **Show** works as the notice's button does and selects the tip. **Hide** is not offered then, and neither is **Solo** while branches are soloed. **Show all branches** appears while a branch is hidden or soloed. Choosing a repository opens it as a click in the sidebar does. Choosing a branch selects its tip as a click on the branch does, and says so when the graph hides it. On the Settings screen the palette lists only the settings pages, **Toggle sidebar**, and **Back to repository**. Each action shows its shortcut, with ⌘ for Cmd on macOS. **Add repository** is Cmd/Ctrl+O, **Search history** is Cmd+F on macOS or Ctrl+F elsewhere, **Undo** is Cmd+Z on macOS or Ctrl+Z elsewhere, **Redo** adds Shift, and **Back to history** and **Back to repository** are Escape. Cmd/Ctrl+P does nothing while a dialog is open or while you type in a text field, and it never opens the browser's print dialog.

The repository list, the last active repository, and which repositories are expanded survive reloads and restarts in versioned local storage. Right-click a repository and choose **Remove** to remove it, or focus it and press Shift+F10. This removes only the saved entry. It never deletes repository files.

Click **Settings** at the bottom of the sidebar to open **Appearance**. Under **Color scheme**, choose **System**, **Light**, or **Dark**. System follows your operating system appearance. Each preview shows the scheme in the themes you picked. Under **Themes**, pick one theme for light mode and one for dark: click a light or dark orb to pick that variant, or click a theme's name to pick both. L1 is the default, and Grove, Ocean, Ember, Iris, and Rose are built in. Picking a light theme while the scheme is pinned to Dark switches the scheme to Light, and the reverse. Click **Create theme** to open a floating panel: name the theme, choose Light or Dark, and set a background and an accent. L1 Git derives the other colors. The graph lanes keep L1's colors in L1's order and start from the lane color nearest the theme's accent, so neighbouring lanes stay distinct for colorblind users in every theme. Status colors stay green, red, and amber, and their lightness, backgrounds, and the shadows follow the theme. Under every theme but L1, a diff colors added and deleted lines with those status colors and highlights code with syntax colors derived from the accent. **Advanced** lists every color for editing. The app shows the draft while the panel is open and returns to your saved theme when you cancel or press Escape. Each theme card has a duplicate button that opens the panel with that theme's colors. Your own themes also have a delete button. Deleting a theme sends light or dark mode back to L1 if it used that theme. Click **Add theme** to import theme files: choose or drop `.json` files, or paste theme JSON. L1 Git reads its own theme format, which L1 Data shares, and VS Code color themes, comments and trailing commas included. A VS Code theme's workbench colors map onto L1 Git's surfaces, text, accent, file status colors, and graph lanes, and its TextMate token colors onto the diff's syntax colors. As in VS Code, the last rule that names a scope wins. A single file that uses `include` is rejected, because the theme it includes is not in the file. Import that theme's extension from Open VSX instead. The same dialog searches the Themes category of [Open VSX](https://open-vsx.org), with **Dracula**, **Catppuccin**, **Nord**, and **Tokyo Night** as one-click searches. Picking a result downloads the extension, follows its manifest and `include` chains, and adds one theme card with every variant it contributes, light and dark. Cards with three or four variants shrink their orbs to keep one row. The desktop app's content security policy allows `open-vsx.org` and `openvsx.eclipsecontent.org`, where Open VSX serves the downloads. Open **Fetching** to choose how often L1 Git fetches in the background: **Off**, 5, 15, 30, or 60 minutes. The default is 15 minutes. Background fetches wait while the window is hidden and catch up when you return. L1 Git always fetches at launch and when you click **Fetch**, even when the schedule is Off. The app saves both choices on this device. Click **Back** or press Escape to return to your repository, with the selected commit and the open diff preserved.

## Run the browser preview

```sh
pnpm dev
```

Open <http://127.0.0.1:1422>. The browser uses the same Rust core through a development-only loopback bridge on port 9417. The Add dialog accepts a local absolute path. The native directory picker is available in the desktop app.

The bridge accepts JSON POST requests only from the development origin, on one route, `/api/run`. Each request names its operation in an `op` field. A successful answer is `{"op": ..., "data": ...}` with the same `op`, and the bridge adds `"ok": true` to it. A repository error comes back as `{"ok": false, "error": ...}`. The bridge rejects an unknown operation, a missing field, or an unknown field with status 400 and a message that names the problem. It exposes the same reads, fetch, fast-forward, and writes as the app. The writes are `write`, `undo`, and `redo`, and `undoHistory` reads the undo history. The reads are `snapshot`, `refs`, `commitDetail`, `lineStats`, `filePatch`, `fileHistory`, `blame`, `worktreeStatus`, and `worktreePatch`. `fileHistory` and `blame` take an `oid` and a `file`. `fileHistory` returns each commit that changed the file, with the file's path in that commit. `blame` returns the file's text and its line ranges, each with the commit ID, author, email, time, and subject that last changed it, or `binary` or `tooLarge`. `commitDetail` and `filePatch` take a `comparison` with a `base` and a `target`. The base is `{"kind": "firstParent"}`, which means the target's first parent or the empty tree for a root commit, or `{"kind": "commit", "oid": ...}`. The target is `{"kind": "commit", "oid": ...}` or `{"kind": "worktree", "root": ...}`, a worktree of the repository compared with its files on disk. A worktree target needs a commit base. `overview` reads branch status and can fetch first. `fastForward` moves branches. `lineStats` counts added and deleted lines for up to 500 commits at once, so the history reads them only for the rows on screen. `refs` returns the root, name, HEAD, branches, tags, stashes, and submodules, so the sidebar can list a repository without reading its history. `snapshot` returns the same refs with the history. `write` takes an `operation` and an `expect`, described in [What L1 Git changes](#what-l1-git-changes). `undo` and `redo` take the `id` of the entry that `write` or `undoHistory` returned. A request body can be up to 4 MiB. The bridge is not included in the native app. The bridge keeps undo history in `L1GIT_UNDO_DIR`, or in `l1git-undo` under the system's temporary folder when that variable is unset. To run another isolated instance, choose both ports:

```sh
L1GIT_DEV_PORT=1423 L1GIT_BRIDGE_PORT=9418 pnpm dev
```

Every read and every write has a deadline. When the deadline passes, L1 Git stops Git and every process Git started, such as a clean filter, and the request returns a `timedOut` error that names it and asks you to retry. A stopped write also says what it left behind. The inspector shows it with **Retry details**. A history read that times out shows it with **Try again**, above the last history it read or in place of a history it never read. Each deadline is about 100 times or more the read's run time on the `pnpm fixture:large` repository:

| Read or write | Deadline |
| --- | --- |
| `snapshot` | 120 s |
| `refs`, `lineStats`, `worktreeStatus`, `worktreePatch`, `undoHistory` | 30 s |
| `commitDetail`, `filePatch` | 20 s |
| `fileHistory`, `blame` | 60 s |
| Branch status in `overview` and `fastForward` | 60 s |
| `write` of `stageFiles` or `unstageFiles`, `undo`, `redo` | 120 s |

A deadline covers all of a read's or a write's Git commands. A write's deadline starts again once it holds its locks. Branch status is the exception. Its deadline starts again after each fetch, checkout probe, branch move, or fast-forward merge, because those commands have their own deadlines, and after waiting for another fetch or fast-forward of the same repository to finish.

A read waits for Git's error output only when it reports a failure, and then for at most 1 s after Git exits, so a filter that leaves a background process running cannot hold a read open. Each Git command runs in its own process group, so Ctrl-C or closing the terminal does not reach it directly. The native app and the development bridge stop every Git command still running when they quit, including on Ctrl-C, SIGTERM, SIGHUP, or SIGQUIT. They wait up to 1 s for a Git command that is starting to be listed, and refuse to start new ones. Then they wait up to 1 s for each write that was stopped to delete its lock and its copy of the index. A write that reaches the index after quitting began takes no lock and answers that L1 Git is quitting. Quitting can take about 3 s when a Git command is slow to start and another ignores SIGTERM. A force quit or SIGKILL skips this step. To try a short deadline, start the bridge with `L1GIT_READ_DEADLINE_MS`, which lowers each read deadline to at most that many milliseconds. It does not change write, fetch, or fast-forward deadlines.

`worktreeStatus` lists one worktree's changed paths. These are staged and unstaged edits, renames and copies, conflicts, submodules, and untracked files. Each tracked entry carries the index entries Git reported for it: `index` for an ordinary path, `index` or `original` on a rename's `side`, and the three `stages` of a conflict. A write sends these entries back as the view it acts on. `worktreePatch` takes a `file` from that list and a `side`. `staged` diffs HEAD, or the empty tree before the first commit, against the index. `unstaged` diffs the index against the working tree, and covers untracked files. A conflicted path returns its conflict and its diff against HEAD. That diff is absent for a submodule, for a file gone from the working tree, and for a file that matches HEAD. A staged submodule change returns its gitlink diff, and an unstaged one returns the submodule's state instead of a diff. An untracked file's patch is Git's own diff of the file against nothing, so it shows what `git add` would stage, after `.gitattributes`, line-ending settings, and clean filters such as Git LFS. On macOS and Linux, L1 Git first reads the file without following symbolic links, then checks that Git's blob ID and shown text match those bytes. If they differ, the read fails and asks you to refresh. Other systems cannot read untracked file patches. A file larger than 1 MiB on disk returns its file size instead of a diff, and Git output larger than 1 MiB returns the patch size. If a required filter fails, the read returns Git's error. A file replaced by a named pipe during the read makes the read time out instead of waiting forever. Paths inside a `.git` directory are refused. L1 Git runs no Git command that writes for either read. A clean filter, such as Git LFS, can still store objects, as it would for `git diff`.

An untracked file's patch differs from `git add -N` followed by `git diff` in these cases:

- Git reads `.gitattributes` from the working tree. A `.gitattributes` file deleted from the working tree but still in the index is ignored.
- A clean filter whose output changes between runs always fails with the refresh message.
- A top-level file named `-` reaches Git as `./-`, so a filter that uses `%f` sees `./-`.
- The size check runs first, so a required filter that fails on a file over 1 MiB returns the size instead of the error.
- External diff drivers and `diff.mnemonicPrefix` do not apply, as for every other diff in L1 Git.

Recents belong to each browser origin or the native WebView. The native app and browser preview have separate saved lists.

## What L1 Git changes

The Rust core runs four Git commands that contact a remote or move a branch:

- `git fetch <remote>` for each remote that does not set `skipFetchAll` or `skipDefaultUpdate`. It updates only remote-tracking refs under `refs/remotes/`. Git 2.48 and later can also create `refs/remotes/<remote>/HEAD`. It follows your `fetch.prune` setting and does not write `FETCH_HEAD`.
- A dry-run `git fetch . <commit>:<branch>` that asks Git whether a branch is checked out in any worktree. It writes nothing. It runs only when some worktree has a detached HEAD, as a rebase or bisect leaves it. L1 Git does not move a branch when this check cannot answer.
- `git update-ref` to move a branch that is not checked out. The branch moves only from the commit you saw to the upstream commit you saw.
- `git merge --ff-only` inside the worktree of a checked-out branch. It runs only when that worktree has no uncommitted changes to tracked files and no merge, rebase, am, cherry-pick, revert, or bisect in progress. Git refuses it when the update would overwrite an untracked file.

It also writes the index of one worktree, through the `write` request:

- `stageFiles` runs `git add` for each entry's paths. It stages what is on disk, and it marks a conflicted path resolved. Staging an unstaged rename stages both of its paths.
- `unstageFiles` runs `git reset` for each entry's paths. That puts HEAD's version back in the index, or removes the path before the first commit. Unstaging a staged rename restores both of its paths. A conflicted path is refused, because `git reset` would keep HEAD's version without a word.

Paths always reach Git as literal names, so `*` and `[x]` match only themselves. L1 Git does not stage a nested repository. A name that is not valid UTF-8 reaches the app with U+FFFD in place of its bad bytes, in `worktreeStatus` and in a refusal's `paths`. A write answers `unsupportedPath` for a chosen name that such a name reads as, and so also for a valid name beside it that reads the same, because L1 Git cannot tell which one you chose.

A write changes only the paths its entries name. L1 Git reads the whole index before and after Git runs, and if Git changed any other path, the write answers `staleView` with reason `pathNotChosen`, lists those paths in `paths`, and changes nothing. That happens when a folder replaced a file or a file replaced a folder, because Git would also add or remove the paths on the other side, such as `z/x` when you stage the deleted file `z`, or `z` when you stage `z/x`. Choose both entries to stage or unstage them together. In a repository that ignores case, as macOS repositories do by default, Git stages a new file under the spelling the index already uses for its folder. So after you rename the folder `Dir` to `dir` on disk, staging `dir/b` would stage `Dir/b`. Then the write answers `unsupportedPath`, names both spellings, and changes nothing. That answer lists no other path Git would also change, so once the names match, the next try can answer `pathNotChosen` for those.

L1 Git runs at most one fetch or fast-forward at a time per repository, and at most four fetches at once. It also runs at most one write, undo, redo, or branch move at a time per repository. A write never waits for a fetch. It never creates merge commits, rebases, commits, pushes, or checks out.

### A write goes ahead only if the repository still matches what you saw

A `write` names the worktree and an `operation`, either `{"kind": "stageFiles", "entries": [...]}` or `{"kind": "unstageFiles", "entries": [...]}`. The entries are `worktreeStatus` entries, sent back unchanged with every field, `null` ones included. Its `expect` is `{"head": ...}`, the HEAD that `worktreeStatus` returned. L1 Git creates `.git/index.lock` itself, so another Git process that writes the index fails as it does during any Git write. Then it compares HEAD and each path's index entries, by mode, object ID, and stage, with what the request carries. If any of them changed, the write answers `staleView` and changes nothing. If another process holds `index.lock`, the write answers `lockHeld` and changes nothing. Git runs on a private copy of the index, `.git/l1git-index.<pid>`, which keeps the index's modification time, so Git still compares the contents of a file edited in the same second the index was written. L1 Git renames the copy over the index only after the write and its undo entry are recorded. Each command on the copy sets `core.splitIndex=false`, so Git keeps the copy whole and never creates or deletes a shared index file during a write. A write, undo, or redo that is refused leaves a split index exactly as it was. The index one puts in place is whole. With `core.splitIndex=true`, Git splits it again at its next write, and an index split only by `git update-index --split-index` stays whole. A write that changes nothing answers `unchangedPath`.

A `staleView` error carries a `reason` beside its `message`: `headMoved` when HEAD is not the one the request or the undo entry names, `pathChanged` when a path's index entries differ from it, `pathNotChosen` when Git would also change a path the request does not name, with those paths in `paths`, and `historyChanged` when an `undo` or `redo` names an entry that is not next.

Writes set `GIT_EDITOR=:`, so no write opens an editor. They set `GIT_REFLOG_ACTION` to `l1git stage`, `l1git unstage`, `l1git undo`, or `l1git redo`. Staging and unstaging commit nothing, so no commit hook runs and nothing is signed. Git runs no hook while it changes the private copy. Each of its commands sets `core.hooksPath=/dev/null` and turns off, by name, each hook that config defines for `post-index-change`, through `--config-env`, so a name that holds `=` stays whole. After L1 Git replaces the index and lets go of its locks, it runs `post-index-change` once with `git hook run`, from the worktree root and against the real index, when you have a hook file or a config hook for it. Its first argument is `0`, because no write changes the worktree. Its second is `1` when the write or the restore touched an entry with the skip-worktree bit, and `0` otherwise. A write that fails or changes nothing runs no hook. L1 Git ignores how the hook ends, as Git does.

### Every write can be undone

`write` answers with the entry it recorded, `{"id", "root", "operation"}`. `undoHistory` answers with the next entry to undo and the next to redo. `undo` and `redo` take the entry's `id`. If the id is not the next entry in that direction, the request answers `staleView`, so an undo never acts on an entry you did not see. Repeating an `undo` or `redo` that already happened answers the same entry and changes nothing.

An undo puts back the exact index entries the write replaced: conflict stages, intent-to-add entries, and skip-worktree and assume-unchanged flags. A redo puts back the exact entries the write left. Both refuse with `staleView` and change nothing when HEAD moved, when any of those paths changed since, or when putting them back would change any other path, such as a file staged since in place of a folder above them or a file staged since below them. In a repository that ignores case, Git puts a path back under the spelling the index now uses for its folder, and then the refusal names both spellings. One history covers every worktree of a repository. A write past 100 entries deletes the oldest, and a new write deletes the entries you could still redo.

The undo history lives outside your repository, so `git gc` there cannot delete what an undo needs, and no push can publish it. The native app keeps it in its app data folder under `undo`. Each repository gets a folder named by the SHA-1 of its Git common directory. The folder holds a `lock` file that one write at a time holds, `log.json`, and `entries/<id>/` for each entry. An entry folder holds `applied.json`, the answer `write` gave, `change.json`, the index entries before and after, and `objects/pack`, a Git pack of the blobs those entries name. Deleting the oldest entry deletes its folder. `log.json` records the common directory's device, inode, and creation time. A repository deleted and created again at the same path has a new common directory, so it starts with an empty history, and the old entries go at its next write. L1 Git refuses to keep history in a folder that another user owns or can write.

The compiler checks part of this. Every `match` on `Operation` and on the recorded `Change` names each variant, and `write/mod.rs` denies clippy's two wildcard lints, so a new operation without a recorded `Change` does not compile, and neither does a new kind of `Change` without a restore. The compiler also gates the write runner, `git::Write`, and index publishing. The runner needs the transaction in `write/txn.rs` to start, and every command it starts uses the transaction's private copy as its index. Only the transaction's two commits replace the index: one after the store records a new entry, the other for the undo or redo of the entry the log names next. So a command on the write runner cannot reach the index before its record.

The compiler checks nothing else. The read runner, `git::run` and `git::read`, takes any arguments, so it can run a command that writes the index or the worktree. `git::mutate` runs fetches and branch moves, and the fast-forward's `git merge --ff-only` updates the index and the worktree outside the transaction and records no undo entry. The write runner can run a command that changes the worktree, such as `git checkout-index`, which no `Change` records. The compiler does not check that a `Change` records everything its command changed, or that a restore puts it back, so a restore that does nothing compiles. For the index, the whole-index comparison refuses at run time any change a write's entries do not name. The rest is checked by review and by each write PR's audit lane, and each new kind of write is proven by its PR's undo lane.

### What a stopped write leaves behind

A write that fails, times out, or is stopped when L1 Git quits leaves the index unchanged, and it deletes its lock and its copy of the index. A force quit or a crash inside the write can leave `.git/index.lock`. Then every Git command in that worktree reports that another Git process seems to be running. If no Git process is running, delete `.git/index.lock`. It can also leave the copy `.git/l1git-index.<pid>`, or the folder `.git/l1git-intent.<pid>` that an undo of an intent-to-add entry uses. L1 Git deletes them at its next write in that worktree. In the undo folder it can leave `log.json.new` and an entry folder that the log does not name, which the next write deletes.

A crash between recording a write and replacing the index leaves the entry pending in `log.json`. The next `write`, `undo`, or `redo` in that repository settles it before anything else. It keeps the entry when the index holds what the write wrote and HEAD has not moved, and drops it otherwise, so an undo never offers a write that never happened. Until then, `undoHistory` does not offer the pending entry. A crash in an `undo` or `redo` after it replaced the index leaves the log one step behind. Repeating that step finds the index already there, changes nothing, and moves the log on.

Writes are tested on macOS and Linux only.

Fetch uses your SSH agent, credential helpers, and `core.sshCommand`. It ignores `GIT_SSH_COMMAND` and other `GIT_*` environment variables. L1 Git never prompts for a password, passphrase, or host key, so a remote that needs one reports an authentication failure. A fetch from one remote that takes longer than 5 minutes stops and reports a timeout. The local reads before and after a fetch use the branch status deadline. Error messages omit credentials from URLs.

GitHub owner/repository labels come only from recognized HTTPS or SSH URLs. Displayed remote URLs omit credentials. Other hosting providers are outside this slice.
